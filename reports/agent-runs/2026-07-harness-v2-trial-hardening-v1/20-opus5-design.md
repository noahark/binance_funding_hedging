## 1. 总判断

来源文档的核心归纳是对的，且比它自己说得更狠：**v2 保留了 v1 的规则，删掉了 v1 的
机制**。G1、G14、G15、G12 是同一个物种。但"机制"不等于"把 v1 搬回来"——v1 的
2,414 行 validator 与 154 行 JSON schema 被删是正确的，错的是替代物为零。

本设计因此有一条贯穿全文的取舍：**用"最小可执行机制 + 单一散文权威"替代"schema +
校验器 + 注册表"**。新增可执行文件只允许一个，且它被显式声明为从属于
`AGENTS.md` §7 的机制，不是第二权威。

十九条 G 的处置分布：**接受 9 条、改写 6 条、拒绝 2 条候选修复（问题接受）、延后
1 条、已有归属 1 条**。W1–W6 全部保留，且每条都给出本设计里可能伤到它的具体路径与
防护措施。

## 2. 逐条裁决（G1–G19）

裁决口径：`接受` = 问题真实且候选修复可用；`改写` = 问题真实但候选修复会伤到 v2，
另给方案；`拒绝` = 候选修复被否（问题本身仍可能成立，另行说明）；`延后` = 证据不足
以现在动手；`已有归属` = 已被现存文件拥有，不重复立项。

### G1 评审闭包既无 schema 也无校验器 — **接受（与 G14 合并）**

问题成立且已两次真实发生（shell 展开、终端换行导致 verdict 损坏）。
`AGENTS.md:118` 的"缺失或含糊的评审闭包数据非 accepting"是 §3.7 安全内核条款的
落地句，**不能按候选修复的第二选项删掉它**——删掉等于削弱安全内核。

改写点在实现形态：**不恢复 `schemas/review-verdict.schema.json`**。v2 的 verdict
不再是 JSON，而是结果块内的三行中文闭包。给它一个 JSON schema 会同时做三件坏事：
把 verdict 推回 JSON 形态、在 §7 之外建立第二个形状权威（违反 §2）、把 154 行文件
重新引入启动面。正确形态是一个**纯文本块语法检查器**，见 §4。

### G2 无计划/设计评审步骤 — **接受（按其推荐的最窄形态）**

`AGENTS.md` §6 从第 1 步直接到第 3 步，§8 只在交付边界路由 review-1/review-2，
确无独立读者审阅"实现者将碰与不碰什么"。本阶段的临时 Codex 计划评审返回 `REWORK`，
命中缺陷家族源头站点与一处事实错误——这是可计价的收益。

形态：**§8 增加一句**，仅 `HIGH_RISK` 适用，只读、跨 provider、一轮，verdict 回到
Planner。**不新增角色、不新增技能、不改 `rework_count`**——因为 `AGENTS.md:182`
既有的"pre-dispatch packet correction 不计数"（即 W4）已经覆盖它。这一点来源文档
说要"不触碰 rework_count"，实际是**它本来就不需要任何计数改动**，比它以为的更便宜。

### G3 `base_sha` 定义把记账提交放进评审范围 — **接受问题，拒绝其候选修复**

问题成立：计划、dispatch、每一次 status 修订都落在 `base_sha..delivery_sha` 之间。

候选修复（把 `base_sha` 改成"实现者起步的那个提交"）**会伤到 v2**，理由是硬冲突而
不是口味：`roles.md:253-254` 要求"先写 dispatch，再让最后一次 status 修订指向它，
且交付给人之前不得再改该修订"。若 `base_sha` 必须等于最后一次 status 提交之后的
HEAD，那么这个 SHA 就要写进包含它自己的那次提交——正是 `ledger_sha` 明确声明放弃的
自指。唯一的出路是交付后再 bump 一次修订，而 G17 恰好证明交付后 bump 修订是危险的。
两条候选性质"同时成立"的说法不成立。

改写方案（更便宜、覆盖更广、零 SHA 纪律风险）：**在 §8 加一句评审范围口径**——
评审区间内可能包含本阶段自身的控制提交（dispatch、`status.json`、阶段报告）；它们是
评审者的上下文而非受审交付，针对它们的发现按 G18 的分类规则记为范围外。这条同时覆盖
了实现期间可能出现的任何记账提交，而不只是起步前那几个。

因为它编辑 §8，**与 G18 同一次编辑**，故归入批次 A（见 §5 的批次归属理由）。

## 3. 七个设计问题的正面回答

### 问题 1：一个小检查器如何同时校验普通任务结果与评审闭包，而不重建 v1 的 schema / YAML / 巨型 validator？

因为**评审结果就是任务结果加三行闭包**，一套语法即可覆盖两者。

关键在于给它划死边界——让它在结构上**无法**长成 `validate-stage.py`：

| 允许 | 禁止 |
|---|---|
| 读一个文件路径或 stdin，内含一个结果块 | 读 `status.json`、`ACTIVE.json`、阶段目录 |
| 纯文本行语法检查 | 调用 git、读取任何仓库状态 |
| 仅 Python 标准库 | 任何 schema 文件、YAML、配置文件、注册表 |
| 行号定位的错误信息 + 退出码 0/1 | 判断业务正确性、遍历历史阶段、生成报告 |

它校验的清单（全部来自 §7，无一新增）：开头标记；标签集合与顺序；`执行结果` 三值枚举；
`结果摘要` ≤300 字符硬上限；`检查结果` ≤8 项；三行中文交接标签存在且
`本地北京时间` 匹配 `YYYY-MM-DD HH:MM:SS CST`；评审任务额外三行闭包与 `评审结论`
二值枚举；`[/TASK_RESULT]` 是最后一个非空白输出。加 G16 的三态与 G18 的分类后再加两条：
`contested` 项必须带理由与替代证据路径；`REWORK` 的每条发现必须带范围分类。

规模上限写进验收检查：**≤120 行、零第三方依赖**。这个数字本身就是防复胀装置。

**它不是第二权威**：`AGENTS.md` §7 仍是唯一详细权威；检查器被显式声明为 §7 的执行
机制，冲突时以 §7 为准，且 §7 变更必须与检查器同一次提交。这需要在 §2 或 §7 加一句
"可执行合规检查器是单一权威的机制，不构成第二权威"——列为 Human 决策项 1 的一部分。

### 问题 2：交付之后 `rework_count` 究竟何时递增？哪些回执/计划更正仍然排除？

**递增触发点是"再交付"，不是"发现来源"，也不是"任务 id"。**

规则三句：

1. 对当前**交付物**（work item，即最初被 dispatch 的可交付成果）而言，任何在首次交付
   存在之后、为修复缺陷而进行的新实现任务，**递增一次** `rework_count`——无论发现来自
   review-1、review-2，还是 Bookkeeper 验证。
2. **改名或拆分修复任务不重置计数。** 计数绑定交付物而非 `current_task.id`；只有
   Human 同意的新交付范围才重置为零。
3. 仍然排除（W4 原文保留，只在其后追加上述口径）：pre-dispatch packet correction
   （含 G2 的计划评审，它发生在任何交付存在之前）、Human 需求细化、以及**不含代码
   再交付的产物勘误**（G19）。

由此，来源文档披露的"Bookkeeper 拒收不计数、改名为 `task1b-d5-repair`"这一读法被
**明确推翻**：它消耗预算。这对实现者更严，是有意的——因为宽松读法可被无限利用。

状态词汇需要一个落点。两个方案：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | `current_task.state` 增加第四个值 `rejected` = 验证完成且未通过 | 改动一个封闭枚举（需 Human 批准）；失败在状态上可见，改名藏不住 |
| B | 保持三值，拒收表现为 `verified` + `blockers` 非空 | 零枚举改动；但 `verified` 被重载，读者可能误读为"已通过"，且失败被埋进数组 |

推荐 A。理由：G15 的病根就是"这件事没有词汇"，用 `blockers` 表达等于把状态藏进自由
文本，正是可被利用的形态。代价诚实说明：这是对 v2 封闭枚举的一次扩张。

### 问题 3：实现者如何在不静默放过失败闸门的前提下质疑一个错误的验收检查？

`检查结果` 的每一项标注 `pass` / `fail` / `contested`。`contested` 必须携带三样东西：
被质疑检查的原文名称、质疑理由、替代证据（可执行命令或已提交路径）。

三条硬规则，缺一不可：

1. **`contested` 不等于 `pass`。** 只要存在 `contested` 项，`执行结果: completed`
   都**不可封存**，Bookkeeper 必须显式裁定后状态才能推进。
2. **裁定二选一并各有后果**：驳回 → 该检查成立，走一轮修复并递增 `rework_count`；
   采信 → Bookkeeper 按 G19 以勘误更正那条错误的验收检查，**不消耗返工预算**（因为
   缺陷在 packet 不在交付）。
3. 检查器强制形状：`contested` 项缺理由或缺证据路径 = 结果块不合规。

这样"诚实路径"成了被文档记载且最省事的路径，而"把定义放宽直到检查变绿"这条最廉价的
歪路被第 1 条堵死——因为放宽定义会被记为 `pass`，而 `pass` 的证据要经 Bookkeeper 核验。

### 问题 4：同一根因的两轮修复之后会发生什么？

**第三次点补丁被禁止。** 当连续两轮 `REWORK` 被归因于同一根因时，下一个修复任务必须是
一次**穷举根因扫描**，其产物是一份路径枚举清单（该缺陷家族在受审范围内的全部站点，
含已修与未修），并对清单外的站点给出不适用理由。

三个设计取舍：

- **谁定义"同一根因"**：由评审者在 `问题记录` 中命名，Bookkeeper 在修复 dispatch 的
  `Goal` 里原样引用。**不新增 `status.json` 字段**（保护 W3），根因是散文，不是状态。
- **刹车不新增计数器**：穷举扫描本身仍算一轮，占用既有三轮预算。若穷举扫描仍返回
  `REWORK`，那就是第三轮，`AGENTS.md:182` 既有的"上限三轮后交 Human 选择"接管。
  §2 禁止重复的数值限额，这个设计因此一个新数字都不引入（"连续两轮"是条件不是限额）。
- **拒绝的变体**：给刹车单独设一个 `same_root_count` 字段——那是第二个数值权威，被 §2
  禁止，且与三轮上限的交互需要额外规则。

### 问题 5：早于本次交付的评审发现如何分类？

评审者必须为每条 `REWORK` 发现标注三者之一：

| 分类 | 判据 | 对闸门的作用 |
|---|---|---|
| `in-range` | 由本次交付引入或触碰 | **阻塞交付**，走修复轮 |
| `pre-existing-independent` | 引入提交早于 `base_sha`，且不在本次交付文件内 | **不阻塞**；记入阶段 follow-up / `PROJECT_STATE.md`，作为独立工作排期 |
| `pre-existing-release-critical` | 同上，但涉及资金、实盘闸门、账务含义或安全内核 | **不机械阻塞交付**，但**阻塞合并/发布**，并作为具名决策上交 Human |

三个必须同时成立的配套条款，否则这条规则会被滥用：

1. **分类必须带证据**：`pre-existing-*` 必须引用早于 `base_sha` 的引入提交
   （`git blame` / `git log -L` 输出），**Bookkeeper 封存前核验该引用**。这把"把范围内
   缺陷改标成既存"从口头判断变成可证伪的断言。
2. **不新增第三个 verdict 值**。全部发现皆为范围外时，评审者返回 `ACCEPT`，
   `问题记录` 照常填写路径，`修复要求` 指向 follow-up 或 `none`。§7 只说"`REWORK`
   需要发现"，从未禁止 `ACCEPT` 携带发现——因此这条规则**零枚举增长**。
3. **全子系统扫描的指令保留**（W-类价值）：分类改变的是发现的去向，不是评审的广度。

代价明说：此后一个 `ACCEPT` 可能同时附带一条已记录的实盘资金 follow-up。Human 必须
知道"接受交付"不再等于"系统在该路径上是干净的"。这是 Human 决策项 4。

### 问题 6：不可变原始输出、已封存证据、草稿、勘误四者如何区分？

| 类别 | 定义 | 可否编辑 | 更正方式 |
|---|---|---|---|
| 原始输出 | 模型结果块、测试日志、verdict 原文 | **永不编辑** | 仅追加清晰标记的勘误块或独立勘误文件 |
| 已封存证据 | 处于受审 `base_sha..delivery_sha` 内的一切 | 评审期间冻结 | 只能写勘误文件——就地编辑会移动受审范围 |
| 草稿 | 尚未交接/交付的文档 | 自由编辑 | 无需勘误 |
| 勘误 | 对已交付内容的更正 | 只增不删 | 注明日期、作者角色/模型、原错误、正确内容、证据；**绝不删除原文** |

外加一条归属规则（Bookkeeper 当场发明、值得固化）：**自己的已交付文档可以就地更正，
但必须附带日期说明改了什么、为什么；他人的已交付产物只能追加显著标记的勘误，不得编辑
其散文。** 落点：`roles.md` Shared Rules 的"Preserve raw evidence"旁边——那里已经拥有
"不得用叙述摘要替换原始输出"，勘误是它缺的另一半。

### 问题 7：哪些被提出的修复会削弱 v2 或恢复重复权威？

## 10. 给 Human 的中文建议

**发生了什么。** 我核对了十九条问题里每一条的证据，全部能在仓库里复现，没有一条是
凭空的。但**有九条被提出的"修法"如果照做，会让新流程变差**——它们会把上一版刚删掉的
重复文件和重复规则带回来。所以我接受了问题，改写了修法。

**最重要的一句结论。** 上一版流程的教训不是"检查工具太大所以应该没有"，而是"2,414 行
太大，0 行太小"。本设计只加**一个约 120 行的小检查器**，它只看模型交回来的那一段结果
文字，不读数据库、不读状态文件、不碰 git——这样它长不成上一版那个庞然大物。

**实际效果。** 分两批做：第一批堵住闸门漏洞（结果格式没人检查、返工轮次能靠改任务名
绕过、实现者无法申诉一个错误的验收标准、评审时发现的旧毛病会卡住无关的交付）；第二批
做已被证实的卫生问题（工作树忘记切分支、决策没地方写、2 KB 状态文件没有淘汰规则等）。
清理 43 个历史目录是第三件事，因为它会真删东西，单独授权。

**需要您拍板的选择（共九项）：**

1. **是否允许新增那一个可执行文件**（`scripts/check-task-result.py` 及其测试）。这是两
   批里唯一的新文件。不加的话，格式违规只能继续靠人眼抓——已经漏过一次。
2. **是否允许给任务状态增加第四个值 `rejected`**（"已验证且未通过"）。不加也能做，但
   失败会被埋进备注里，容易被忽略。建议加。
3. **返工次数改为更严的算法**：只要交付物已经交过一次，之后每一轮修复都计数，且**改名
   或拆分任务不清零**。这对实现者更严格，是有意的——旧读法可以被无限绕过。
4. **接受"旧毛病不再卡住新交付"这条规则的代价**：此后一次"通过"可能同时附带一条已记录
   的资金相关待办。也就是"接受这次交付" ≠ "这条路径已经干净"。建议接受，因为另一条路
   是每次交付都被全系统旧账绑架。
5. **分段阅读的阈值数字**：建议 32 KB（单个文件不得吃掉超过一半的阅读预算）。这是没人
   定过的数，需要您给一个。
6. **模型启动命令文档是否现在恢复**：建议**先不恢复**，只记为待办。上一版那份文件有 454
   行且和另一份路由文件绑在一起，恢复它很可能把已删掉的重复规则一起带回来。若您希望现在
   就有，可以做一个"只写启动命令、不写模型选择与可用性"的受限版本。
7. **是否允许第一批多带两件小事**（评审范围口径 G3、勘误规则的那一句 G19）。理由是它们
   和第一批改同一节文字，分开改会互相覆盖——和您用 D-7 把同根因刹车折进本批次是同一个
   道理。建议允许。
8. **提案目录的定性**：建议定为"草稿"，即阶段文档不得再把它当证据来源；需要长期保留的
   东西必须提交进仓库。代价是失去提案历史的引用能力。
9. **43 个历史目录的清理授权**——这件事会真的删除文件，建议等前两批做完再单独决定。

**风险提示。** 本设计不曾修改任何 Harness 文件、产品文件或状态文件，也没有触碰仍在运行
的产品阶段。实现开始之前还有一道对账门：产品阶段合并之后，要把这期间新出现的问题重新
