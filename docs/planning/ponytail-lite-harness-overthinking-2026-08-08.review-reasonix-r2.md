## 三、对 v2 §11 六个问题的独立回答

### Q1 v2 是否仍可能压掉真实低概率高损失问题？

独立构造六类候选反例逐一试门：

1. **推导型资金风险（1000x 同型）**：乘数映射在表、两腿共用 `q_common` 为前提 →
   凭据"单位/倍率/取整公式的直接推导与样本" → 条件 2 准入。✓
2. **并发透支（F1-P1 同型）**：两个真实入口 + 共享可变状态 + 无互斥 → 凭据清单明列。✓
3. **omission（regular-spot `-2015` 裸空同型）**：交易所契约允许的事件 + 我方缺少处置
   分支 → 凭据清单明列。✓
4. **展示误导（F4 同型）**：有代码证据（`fetch_um_positions` `None→[]` 降级）→ 条件 1
   准入。✓
5. **证不到的资金场景（51169 平台级抵押额度同型）**：评审者只读、结构上取不到凭据 →
   v2 原文"预计反复出现才留一行观察"会静默丢弃 → **唯一缺口**，opus5 C3 修订后闭合
   （触及资金保留项即可在评审证据留一行，不受"预计反复出现"限制）。✓ 修订后
6. **走私尝试（"加个检查很便宜"）**：§4 已把 cheap-check 从准入条件移除。✓ 挡掉

未找到 v2 修订后仍被误压的当前可达资金场景。门在资金场景上"薄"（条件 2 对资金相邻
代码近乎全覆盖）是"低概率高损失不得忽略"的必然代价，不是缺陷——真正的影响是预期
效果打折（60% 若恰集中在资金场景），opus5 建议的"记录每条发现走条件 1 还是条件 2"
是唯一能在试运行内便宜测出"门是否咬住"的信号，我支持。

### Q2 哪条文字仍可能被用来扩大范围或制造 REWORK？

- **"`文件:行号` 与可追踪控制流"**：真实存在的 file:line 可被夸大为场景入口而触发前提
  不成立。v2 的"仅写'代码里有这个分支'不构成凭据"堵了最粗口子（这句务必保留原样），
  二次防线"对当前交付的具体影响 + 为什么必须本轮修"挡掉大部分，残余交试运行。属任何
  证据门的固有面，非阻塞。
- **条件 2 对资金场景近乎全覆盖**：如上，这是安全方向的设计后果，不改文字，改观测。

### Q3 不扩展 `contested`、不建排除账本、暂不改 reviewer skills 是否有工作流缺口？

- **reviewer skills**：无缺口。v2 §8 触发式处理（试运行证明持续覆盖再另开任务）自洽。
  唯一要求是触发信号必须有人看——支持 opus5 非阻塞建议：§10 加观察项"评审者是否以
  skill 文本（如 `reality-checker.md` 的 `Default to finding issues`）对抗 §1 准入"，
  否则该条款休眠。
- **排除账本**：无安全缺口。v2 §3"Human 确认后进入现有持久权威"复用
  `DEC-2026-08-07-007` 先例。两个补充：(a) 明确模型可在报告里**提议**某条目由 Human
  确认，否则通道无人发起（与 opus5 v2 补充一致）；(b) 对 glm-5.2 的跨阶段去重建议，
  我独立评估后认为与 (a) 收敛——"评审者提议 → Human 在读 `PROJECT_STATE.md` 时确认或
  撤销"既防同一批假设跨 stage 回流，又不给模型单方面写永久权威的权力，采纳成本为零。
- **`contested`**：我 v1 未主张扩展，现独立复核 opus5 的撤回——成立。"是不是资金类"
  本身是争议点，让 Bookkeeper 消解 Reviewer verdict 是安全回退；有界回退（review-2 →
  `rework_count` 上限 → Human）对安全充分。支持 opus5 可选建议（Human 认定不合规的
  发现不递增 `rework_count`）：与既有"缺陷在 packet 不在交付"豁免同构，只改计数不改
  权限，但列为可选，v2 不采纳也不阻塞。

### Q4 三文件范围与单一权威安排是否成立？

**成立。** §3 落 `AGENTS.md` §1（既有原则的执行口径，非新章节）、§5 落 §8（既有 Review
Rules）、§6 补 discipline 现文件缺的三点（非平行阶梯）、§7 一条 override 指向
discipline（不复制规则）。我核过 `senior-developer.md` 现有 override 段结构（Obey
AGENTS.md / Use raw task inputs / No credentials 三条），新增一条指向 discipline 的
降权规则与其并列不冲突、不复制清单，且"不写死单进程 / SQLite / 端口等易变事实"的
约束正确（opus5 撤回其 v1 中要把部署形态写进 skill 的建议，我同意撤回）。

两处 §2 单一权威的小瑕疵，支持顺手修（非阻塞）：§5 重述凭据要求应改引用 §3/§1；
§3 凭据清单 9 条前加"本清单为示例，不穷举"（即 C4）。

### Q5 第 9 节案例能否区分"真实安全发现"与"无证据假设"？缺哪个关键案例？

14 行案例覆盖了提出方向的全部判别要点。**结构性缺口：全部是"提出"方向，没有一条是
"驳回/分类"方向**——正好对应 C2/C3 两个安全反例。支持 opus5 新增 4 例（"没找到调用方"
驳回资金场景不成立；是否命中保留项存疑按高损失例外；评审者取不到凭据的资金场景留观
察；凭据形状不在清单内按示例非穷举）。

### Q6 是否存在更小且同样安全、可验收的修改？

v2 已接近最小（砍六字段模板、砍完整阶梯、discipline 只补三点、cheap-check 移出门外）。
§3 凭据清单 9 类每类对应一种真实缺陷形状，砍任一类都会让门更易误拒真实证据（与安全
反向），不能砍。§7 已是一条 override。支持 opus5 的顺手瘦身（凭据清单压到 3 行 +
"示例非穷举"、§5 引用不重述），合计约减 8 行常驻启动文字，且都是 §2 单一权威的直接
要求。无更小的独立替代方案。

## 四、新增建议 N1（非阻塞）：试运行任务构成须含至少 1 个资金路径任务

v2 §10 说"用连续 5 个正常任务观察行为"，未限定任务构成。若 5 个任务全是前端 UI /
纯展示类任务，则资金侧行为观察为零——试运行对"资金安全例外是否被正确执行"无信息量，
而那是本方案风险最高的部分。建议 §10 补一句："5 个试运行任务中至少 1 个命中资金、
订单、持仓、划转或账务路径（或明示试运行结论不覆盖资金侧，资金侧另行验证）。"kimi
v1 曾提过相近建议，我独立到达同一点并认为 v2 应把它写死，否则试运行结论对资金侧
无效。
