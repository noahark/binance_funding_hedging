## 总体判断

**ACCEPT（可进入 Human 决策）。** 方向正确：要治理的是"凭理论可能就扩范围、就 `REWORK`"，
不是要模型不看边界条件；资金安全例外的口径（§2 末段、§4 条件 4、§6 末段）守得住，
验收案例表（§8）也选得准——尤其是"便宜断言应验证，不以 YAGNI 删"和"一行实现隐藏单位/

但有两个问题要在 Human 决策前由 Planner 收口，**不是阻塞计划成立，而是落地文字前必须改**：

1. **§4 条件 5 作为独立 OR，会反向打开"无限加检查"的口子**——这正是 Human 痛点的同源病。
2. **提案 §4/§5 与 `AGENTS.md` §1 + `developer-discipline.md` §2 高度重叠**；
   真正新增的只有两处"牙齿"（§4 的"else 仅非阻塞"落尾、§6 的证据门）。把整套阶梯/六字段/

## 对八个重点问题的回答

### Q1 — 场景准入门是否会压掉必须处理的低概率高损失问题？

**不会，但有一个边界要补。** 条件 4（资金/安全/数据损失/缺失关仓，且静态可达）+ 条件 2
（已发生/可复现/有证据）已经把高损失类接住了；§6 末段"资金等高风险路径不要求等真实事故，
明确静态可达路径即可作为证据"也消除了"没出事就不能 block"的误读。反例我没找到。

唯一缝：**"Reviewer 怀疑一条资金路径可达，但当前无法完整静态证明"** 落进了"均不满足"
的 fallthrough——按现文字最多记非阻塞观察。对普通场景这没问题；对资金路径，"证不到"不该
等于"静默丢弃"。建议在 §4 fallthrough 或 §6 补一句：**资金/关仓类路径若无法证明可达也
无法证伪，记为非阻塞观察并显式上交 Human 决策，不得静默丢弃，也不得无证据阻塞。**
（与 Q5"不与现有风险接受记录冲突"一致。）

### Q2 — "静态可达路径即可作为资金风险证据"的边界是否足够明确？

**基本明确，建议给"静态可达"一个可核验的最小定义。** 现文字散在 §4 条件 3/4 与 §6 条件 2/5。
建议收敛成一句权威：静态可达 = 能给出**入口调用点 + 前置状态 + 关键分支 + 触发输入**，
且这些在当前代码与配置下成立（不是"未来重构后"）。这正好是 §6 的字段 1-3，把它显式绑定
到"静态可达"一词上，Reviewer 就没有"我说可达就可达"的自由度。无需新增字段，只是把已有
三字段命名化。

### Q3 — "便宜验证 / fail-closed"会不会反过来成为无限加检查的借口？怎么收紧？

**会，这是全稿最需要改的一处。** 现在条件 5 是独立 OR：满足任一即 admit。一个想加防御的
模型可以说"这个 assert 很便宜、不扩契约 → admit → 我加"。这跟 Human 抱怨的"为低概率场景
叠防御"是同一个洞。

收紧办法（二选一，推荐前者）：

- **把条件 5 从 admit 条件改成"已 admit 场景内的增 privileges"**：cheap-check 不是把一个
  新场景放进门的理由，而是"一旦某场景已由 1-4 admit，允许顺手加一个便宜断言/fail-closed"。
  即条件 5 只修饰 1-4，不能单独开门。文字上把它从五条并列改成附加条款。
- 或保留独立 OR，但加硬约束："仅当该检查保护的是 1-4 已命中的同一场景，且不改变任何对外
  可观测行为（纯 fail-loud、不新增恢复状态、不改变成功路径返回）。"

§8 案例表已有"便宜断言应验证"兜底，所以把条件 5 降级不会误删便宜安全——它只是不再充当
**开门**理由。

### Q4 — Reviewer 六项证据要求是否过重、重复、或仍可被空泛描述绕过？

- **过重？** 不算重，因为它**只针对"用新场景阻塞交付"**（§6 首句"用一个新场景阻塞交付"）。
  in-range 且有失败测试的发现，其 oracle 就是那个测试本身，不另填六字段。**务必在文字里
  点明这一豁免**，否则会误伤正常 bug 的评审效率。
- **重复？** 字段 1-3（入口/可达/前置）与 Q2 建议的"静态可达"定义同源，可合并表述，
  不必机械列六格。
- **可被绕过？** 健谈模型确实能把六格填得像模像样。**唯一真正抗空泛的是字段 5（oracle）**。
  建议把字段 5 升格为**硬闸**：一个阻塞 `REWORK` 若无可执行测试/命令/原始证据路径，或静态
  控制流证明不够具体（"可能""理论上"不算），**整条发现自动无效**，不论其余五格写得多满。
  这一条收紧后，六字段里真正卡人的就一个，其余是辅助。这与提案"不新增 verdict 枚举"一致——
  它不是新 verdict，是 Bookkeeper 核验 `REWORK` 有效性时的判据。

### Q5 — 是否与范围三分类 / 同根因刹车 / Human 风险接受 / 双评审冲突？

**不冲突，且应显式声明不冲突。** 逐条核对：

- **范围三分类**：本门只管"新场景能否阻塞"，不改 in-range/pre-existing 的判定与举证
  （早于 `base_sha` 的提交引用）。提案 §6 末段已写"不削弱"，OK。
- **同根因刹车**：连续两轮同根因仍触发穷举扫描。提案 §8 案例表第 7 行已明确"不得用最小
  修改原则逃避"，OK。
- **Human 风险接受**：Q1 建议补的"证不到也上交 Human"正好衔接既有"已知风险暂不修仍允许
  合并"记录，不重复阻塞。
- **双评审**：本稿自身就是 HIGH_RISK 的计划评审，流程上自洽。

唯一要注意：本门不得被 Reviewer 用来**回避**三分类里 `pre-existing-release-critical`
的上交义务——即不能以"未达本门证据"为由，把一条本该上交 Human 的资金类历史风险降级成
"静默非阻塞"。建议在 §6 加一行反向兜底。

### Q6 — 三文件范围是否足够？需否扩大？

**足够，且建议实际比三文件更小。** 维度：

- `AGENTS.md`：承载场景准入原则 + §8 证据门——正确，单一权威。
- `agents/developer-discipline.md`：承载实现侧最小化方法——但 §5 六级阶梯与该文件已有
  §1-§4（Think/Simplicity/Surgical/Goal-Driven）重叠约八成。**真正新增的只有两点**：
  "先查代码库已有权威模块/共享根因"和"验收通过即停，不顺手重构"。建议落成 2 条 bullet，
  不要落成一套独立阶梯，并**用指针引 `AGENTS.md` 的准入门，不复制五条件**（守单一权威）。
- `agents/skills/senior-developer.md`：见下方"高杠杆点"——这一处改动价值最高。
- Reviewer skills：维持"至多一行指针、不复制字段清单"，同意。

无需扩大。若有人提议同步改 `software-architect.md`/`task-planner.md`，应驳回——前者已要求
拒绝无依据抽象，后者有上位权威。

### Q7 — 哪些文字会被误读为"忽略边界场景"或"为少写代码牺牲正确性"？

四处高风险措辞，落地时需配防误读修饰：

1. **"场景准入门"之名**：字面像"少考虑"。建议正名"当前相关性准入门"或在开篇一句定义
   "本门管的是能否扩范围/阻塞，不是能否思考"——提案 §1 已有此意，把它提到门名旁。
2. **"项目版 Ponytail 决策阶梯"**：Ponytail 在社区语境强关联"一行优先/代码高尔夫"。
   提案 §3 非目标已明确排除"一行优先"，但阶梯名仍带歧义。建议改名"实现最小化判断顺序"，
   并把 §8"一行实现隐藏单位/取整则用较长实现"这条**写进阶梯本体**，不只是案例表。
3. **"概率很低本身不是忽略理由"**（§4 末）：方向对，但"决定因素是可达性/影响/证据/成本/
   资金例外"这句要置于每处可能被截读的位置，避免被断章成"低概率→忽略"。
4. **条件 5（见 Q3）**：现行措辞最易被读成"便宜就加"——既是 loophole 也是误读源，一并改。

### Q8 — 是否存在更小、同样可验收的整改方案？

**有，建议作为首选。** 提案 §8 的验收案例表测的是**行为**（该拦的拦、该放的不扩、便宜断言
不删……），不是文档结构。所以可以用更小的文字改动达到同等可验收性。按杠杆从高到低：

- **Alt A（最小，~2 文件 / ~12 行净增）**：
  1. `senior-developer.md`：把 vendored Backend Architect 的"默认交付物"（熔断/限流/DLQ/
     零停机迁移/分布式追踪/多副本等）显式降级为"证据触发的能力清单，不是默认交付物"，
     指向 `developer-discipline.md`。**——这一条最直接打在 Human 痛点的源头上**（见下）。
  2. `AGENTS.md` §8：加证据硬闸——"非失败测试支撑的阻塞 `REWORK` 须引用可执行/足够具体的
     oracle，否则该发现自动无效。"
- **Alt B（推荐 knee-of-the-curve，~2 文件 / ~15 行）**：Alt A +
  3. `AGENTS.md` §1：把现有"不为假想场景加防御机"补上**操作性落尾**——"未命中任一准入条件
     的场景最多记为非阻塞观察并写明复开触发信号；不得扩范围、不得加防御、不得阻塞、不得
     `REWORK`。" 这就是把 §4 的牙齿接到既有 §1 上，而非新开一节。
- **Alt C（提案本身）**：Alt B + discipline.md 的六级阶梯 + 完整六字段模板 + 十案例表。
  可验收性等同 Alt B，但文字量与重复度更高，且需动三个文件。

**我的建议：落 Alt B。** 它保留了提案的全部"牙齿"（else-非阻塞 + oracle 硬闸 + vendored
降级），砍掉的是与既有权威重复的"脚手架"。若 Human 更想要可机械勾选的显式清单，再上 Alt C
不迟——但那样应先解决 §4 条件 5 与 §5 阶梯的重复问题。

## 一个被提案低估的高杠杆点：`senior-developer.md` 的 vendored 默认值

提案 §7 把这一处列为三个文件之一，但在我看来它是**全案单位文字收益最高**的一处，应排在
证据门之前。原因：现 `senior-developer.md` 的 vendored 文字把"comprehensive security and
monitoring in all systems""circuit breakers, bulkheads, rate limits, dead-letter queues"
"zero-downtime schema migrations""distributed tracing""multi-region replication"等**当作
默认交付物**（原文多处"Default requirement"）。实现模型一加载这个 skill，就被灌输"规模化
机件是默认"——这正是过度思考的**供给侧**。提案把它降级为"证据触发的能力清单"是对症的，
建议落地时：

- 不要复制规则，只加一条 override bullet + 指向 `developer-discipline.md`；
- override 要点名"熔断/限流/DLQ/零停机迁移/多副本/分布式追踪"是**默认不做**，只在出现
  真实负载/故障证据时按需引入——把"证据触发"具体化，否则又会被读成空泛。

这一处单独做，收益可能就覆盖 Human 60% 痛点的一大块。

## 建议验收案例（在提案 §8 基础上增订）

提案十案例已覆盖核心。建议**新增 2 条、修订 1 条**：

- **新增**：Reviewer 怀疑资金路径可达但无法完整静态证明 → 记非阻塞观察**并上交 Human**，
  不得静默丢弃，不得无证据 `REWORK`。（对应 Q1 缝。）
- **新增**：cheap-check 本身不构成 admit 新场景的理由；但已 admit 场景内应加便宜断言，
  不以 YAGNI 删。（对应 Q3，与既有"便宜断言应验证"案例互补，一个讲"加"、一个讲"不能拿它
  开门"。）
- **修订**：提案"需要多个未出现前提……不得 `REWORK`"那条，补后半句——"除非其中任一前提
  涉及资金/关仓且能给出静态可达路径，此时转为上交 Human 的具名风险"。
