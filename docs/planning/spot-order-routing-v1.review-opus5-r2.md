## 1. P0-A（阻塞）— 被接受的环境前提，与方案自己的证据直接矛盾

方案 §2.6 写：

> **已接受的固定环境前提：**部署时使用的 API key 已由 Human 配置 PAPI 与普通现货交易权限……本轮不在运行时验证此项。

方案 §1 据此把权限运行时探测列为非目标。`PROJECT_STATE.md` 也已据此写入
`[OPEN][ACCEPTED-CONFIGURATION-RISK]` 条目，并把 §2.6 标为 detailed authority。

但方案自己在同一轮落盘的第三份侦察证据
`reports/api-samples/2026-08-spot-order-routing-v1/spot-account-capability.json`
记录的实测结果是：

```json
"permissions": ["LEVERAGED", "TRD_GRP_236", "PRE_MARKET"],
"has_SPOT_permission": false,
"blocker": true,
"blocker_reasons": ["permissions does not contain SPOT"]
```

**侦察作者自己打了 `blocker: true`，方案越过了它，并把相反的断言写成了"已接受前提"。**
一个被自身证据否证的前提，现在正通过 PROJECT_STATE 向权威状态文件扩散。

### 公允地说：Planner 拒绝这个字段的技术理由是对的，我上一轮说过头了

§1 写「不把 `/api/v3/account.permissions` 的文字值当作 API key 权限闸门」——
这个技术判断成立，有两个独立理由：

1. `/api/v3/account` 的 `permissions` 是**账户级**，不是 **API key 级**；
2. 币安对部分账户用 `TRD_GRP_*` 交易组权限**替代** `SPOT` 字面值。
   本次实测拿到的正是 `TRD_GRP_236` —— 所以 `"SPOT" in permissions` 的字面匹配
   **很可能是假警报**，`has_SPOT_permission: false` 未必代表真的不能现货交易。

我上一轮称「复用该响应即零成本完整修法」，这一点我说过头了：它只覆盖账户级，
覆盖不到 key 级，且会被 `TRD_GRP_*` 误判。Planner 的反驳成立。

### 但正确的应对是消解歧义，不是断言相反结论

拿到一个 `blocker: true` 的模糊信号，可选项有三：查清、按坏的假设停、或按好的假设走并记录风险。
方案选了第三条，却**没有先把第二、三条之间的那个歧义解掉**，而解法是现成且只读的：

权威面就是方案自己点名并拒绝的 **`GET /sapi/v1/account/apiRestrictions`**（USER_DATA，
签名 GET，无副作用），其 `enableSpotAndMarginTrading` 字段是 **API key 级**的定论，
既不受账户级/key 级混淆影响，也不受 `TRD_GRP_*` 别名影响。一次只读调用即可终结这个歧义。

在它落定之前，PROJECT_STATE 里那一条不是「已接受的风险」，而是**未解决的已知缺陷**。
二者在 AGENTS.md §8 下的处置完全不同：前者可带病合并，后者不能。

### 前提若不成立，实际后果（这一点 §2.6 也没写）

§2.6 只说「普通现货 POST 可能被拒，而并发的 PAPI 合约腿可能已成交」。真实表现链条是：

1. `/api/v3/order` 返回 `-2015`；
2. `domain.py:362` 将 `-2015` 归入 auth 层 → `live_hedge_executor.py:388-392`
   判为 **`LEG_UNKNOWN_QUERYING`**（不确定，需查单）；
3. 与此同时合约腿 SELL 已成交（`live_hedge_executor.py:713-721` 两腿并发）；
4. 查单同样 `-2015` → 10 次重试耗尽 → `SIGNAL_ORDER_STATE_UNKNOWN` → 任务暂停。

操作者看到的是**「订单状态未知，去交易所核实」**，而不是「权限问题」——
真实原因被诊断链条掩盖了，同时账上留着一条裸空。这个"破裂时长什么样"是
PROJECT_STATE 那条 accepted-risk 缺失的「观察方式」要素（AGENTS.md §8 要求
接受记录含：问题事实、可能影响、接受理由、临时限制或观察方式、后续复看条件）。

### 要求

1. 补一次 `GET /sapi/v1/account/apiRestrictions` 只读侦察，落盘到
   `reports/api-samples/2026-08-spot-order-routing-v1/`。
2. 若 `enableSpotAndMarginTrading: true` —— §2.6 前提成立：保留"不做运行时探测"的
   非目标决定（该决定本身合理），但把 §2.6 与 PROJECT_STATE 条目里的**断言换成证据引用**，
   并补写上面的"破裂时长什么样"作为观察方式。
   同时把 `spot-account-capability.json` 的 `blocker: true` 更正或标注为已被
   `apiRestrictions` 推翻，否则证据目录内部自相矛盾。
3. 若 `enableSpotAndMarginTrading: false` —— `blocker: true` 成立：本方案在权限修好前
   不可进入实现，PROJECT_STATE 条目须从「已接受风险」改写为「未解决的前置阻塞」。

## 2. P1-A — regular_spot 不是边缘分支，是约六分之一的可交易全集

方案通篇按"例外"行文（§1「已知不应使用 PAPI 的 bStock，**或**资产出现在……名单时」）。
实测数据不支持这个框架。

本评审用公开只读接口做了一次交集（无凭证、无签名、无下单）：

| 量 | 值 |
|---|---|
| `maxCollateralExceededAsset` 名单规模（本次实测） | **121** |
| 币安 USDT 永续中状态为 `TRADING` 的合约 | 679 |
| 其 base asset 命中该名单 | **114** |
| 占可交易全集比例 | **16.8%** |

命中的不是长尾，而是大量主流标的：`LINK`、`UNI`、`CAKE`、`COMP`、`VET`、`WBTC`、
`FLOW`、`KAVA`、`ZRX`、`ETHFI`、`GMX`、`ROSE`、`MANTA`、`ALT`、`BOME`、`PEOPLE`、
`NEIRO`、`HMSTR`、`BIGTIME`、`C98`、`CFX`、`DYM`、`ILV`、`IOST`、`JOE`、`KAITO` ……
（`NOM` 亦在其中，与 2026-07-28 事故对上）。再加上全部 bStock。

这不改变设计的正确性，但**改变 Human 正在做的那几个取舍的性质**：

1. §2.7「操作者须手工准备普通现货 USDT」——不是罕见回退的兜底，而是约 1/6 标的的
   **主要资金路径**。资金要长期分驻两个钱包。
2. §2.5 新立的运行不变量（普通现货钱包不得持有与策略无关的同标的敞口）——要在
   114+ 个资产面上靠人工长期维持，而非偶尔照看一两个。
3. 这些现货腿落在经典现货钱包 = **不计入 PM 抵押**。个位数标的时无所谓；到 1/6 全集的
   规模，账户的保证金结构会被实质改变（合约空头在 PM 侧失去对应现货抵押）。
4. 名单是**平台级动态量**：同一个币可能今天 `papi_margin`、明天 `regular_spot`，
   两个钱包的资金需求随之漂移，而本轮不做划转。

**要求：** 不改设计，但把这个量级写进 §1/§2（可直接引用本次侦察的 121 项与本表），
让 Human 是在「约 1/6 可交易标的走这条路、资金长期分驻两钱包」的认知下签字，
而不是在「少数 bStock 加偶发触顶」的认知下签字。

## 3. P2

- **P2-A：§2.5 的新不变量没有观察者。**
  §2.5 说「发现数量不一致即作为账户对冲异常由操作者观察和处理」。但
  `PROJECT_STATE.md` 已记录该观察面的三处已知失效：限制 **B**（漂移标记
  *permanently inert*）、限制 **A**（单腿标记只在合约腿完全缺失时才触发）、
  **F4**（账户读不到时仍谎报「交易所无仓」，且横幅只覆盖三条路径中的两条）。
  本轮把一条新的人工不变量挂在了三个已知失效/受限的展示面上。
  §2.5 应写明该不变量的实际观察手段（哪怕结论是「只能人工去币安核对」），
  否则它只是一句无法执行的文字。
- **P2-B：§7 验收清单编号损坏。** 存在两个 `9.`（第 109 行「普通现货使用独立错误产品…」
  与第 111 行「不实现 API key 权限运行时检测…」），且 `10.`（第 110 行）夹在两者中间。
  AGENTS.md §8 把「验收判据不清」列为 HIGH_RISK 触发条件之一，验收清单本身的格式必须修。
  另：第 111 条是一句「不做什么」的声明，不是可验证的检查项，位置应在 §1 非目标而非 §7。
- **P2-C：`openLongRestrictedAsset` 的「不存储」与项目自身取证纪律不一致。**
  §3 定为不校验/不存储/不参与路由。但 §1 对 `51146` 的处理原则恰恰是「仍保留原始响应
  供后续取证」；而且本次实测该数组为**空**，整体留存响应体的成本≈0。
  建议改为「**整体留存**原始响应，只按 `maxCollateralExceededAsset` 路由」——
  路由范围不变，取证能力不丢。

## 4. 逐条回答 §8 的六个评审问题（修订版）

**Q1 「普通现货降级仅限正费率 BUY」是否是充分最小边界？**
**是。** 上一轮我提的唯一缺口（会造出未来平不掉的仓位）已由 §1 的平仓非目标补上，
且写明「按其已保存的实际 route 另行设计」——把 P1-3 的 leg 行权威延伸到了平仓阶段，方向正确。

**Q2 `restricted-asset` 是否被正确限定为单向分流信号？全局 fail-closed 取舍是否可接受？**
**限定：正确。** §3.4 的「未命中只表示本次未观察到平台额度已满，不表示 PAPI 现货一定可提交
或不会返回 51169」、§7.8、以及 `.note.json` 里的 caveat 三处一致，没有把"未命中"读成"可用证明"。
**取舍：可接受，但 Human 签字时的规模认知是错的。** 权重 1、IP 维度、每次开单一读，
成本可忽略；用可用性换"额度已满时不先发 PAPI 现货腿"是合理的。但见 P1-A：
它保护的不是边缘情形，而是 16.8% 的全集——这实际上让取舍更划算，只是 Human 应当知情。

**Q3 route、endpoint、symbol、base asset 是否贯穿全链路？**
**是。** §4 第二条把 `hedge_open_leg.endpoint` 定为唯一权威并同时封堵了 leg 名称与
任务级 route 两个反推源，§7.4 有对应验收，§4.5 的 `PRODUCT_SPOT` 补上了错误码命名空间。
上一轮此项的两个缺口均已闭合。

**Q4 「普通现货钱包只含策略仓位」的运行不变量取舍是否足够清楚？**
**表述清楚，但不可执行。** 不变量本身写得明确（含"可能混入非策略库存"的坦白），
问题是它**没有观察者**（P2-A），且要在 114+ 资产面上长期人工维持（P1-A）。
在补上观察手段之前，这一条是声明而非控制。

**Q5 `51169` 延后补腿的非目标是否足够明确？**
**是，已完全闭环。** §5 三段现在覆盖了红线（等确定性结论、全新 client ID、逐一处理合约腿、
不得伪装为同一 leg）与人工恢复的消歧。无进一步意见。

**Q6 Human 接受不做权限运行时检测后，残余风险是否已清楚记录？**
**否。** 记录的**结构**是对的（风险事实、适用条件、复审触发都在，且已同步 PROJECT_STATE），
但它**建立在被自身证据否证的前提上**（P0-A）——前提为假时，结构再完整也不成立。
此外该记录缺 AGENTS.md §8 要求的「观察方式」要素：前提破裂时系统的实际表现是
`-2015 → auth → LEG_UNKNOWN_QUERYING → 10 次重试 → order_state_unknown 暂停`，
操作者看到的是「订单状态未知」而非「权限问题」，同时合约腿已成交。这一点必须写进
§2.6 与 PROJECT_STATE 条目。
