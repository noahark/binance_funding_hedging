- 作者：Opus 5

- 基线：`main` @ `27cbcaf`

---

## 1. 为什么做这件事

乘数换算方案连续三轮被评审挑出「同一类遗漏」：

| 轮次 | 漏了什么 |
|---|---|
| r1 | 「两腿价差」三个调用点全漏；发单数量只提 1 处（实为 3 处） |
| r2 | 补了后端两处价差，漏了前端第三处 |
| r3 | 由 grok 补齐 |

根因不是粗心，是**同一个概念散在多处实现，按文件打补丁必然漏**。本方案把这两个概念
各自收敛到一处，让乘数轮只需要改一个地方。

**做完之后**：乘数轮的 §3.1 与 §3.5 各少一个改动点，而且少掉的正是最易漏的那两个。

---

## 2. 现状核实（更正一处早前的错误描述）

早前简报曾称「两腿价差有三份彼此独立的实现」。**该描述不准确**，实际是：

### 公式 A —— 盘口价差 `(买一 − 卖一) ÷ 卖一 × 100`

`compute_opening_spread_pct`（`backend/domain/snapshot.py:613`）。

- **已经是单一共享函数，无重复实现**
- 四个调用点：`snapshot.py:698/699`（市场表两方向）、`domain.py:1588/1591`（平滑门两方向）
- **是冻结契约**：函数注释明写 `operation order is frozen (breakdown P2-1)`——
  减法、除法、乘 100、仅对最终结果按 `ROUND_HALF_UP` 量化到 `0.01`，顺序固定。
  平滑门用它做**资金放行判定**，两位量化直接决定放不放行。

→ **本方案不动 A。** 它没有重复可合，且动它是动资金门。

### 公式 B —— 成交均价价差 `(卖出腿均价 − 买入腿均价) ÷ 两者较小值 × 100`

**存在一处真重复，且跨语言：**

| 实现 | 位置 | 用途 |
|---|---|---|
| Python | `store.py:2563` `cycle_slippage_pct` | 历史页滑点 |
| **JavaScript** | `frontend/index.html:5249` `computeHedgeOpenBasisRate`（调用点 `6624`，表头 `6774`） | 持仓表「开单价差率」列 |

**重复的原因是具体的、可消除的**：后端 `open_basis_rate` 字段是**写死的占位 `"0"`**
（`store.py:2860`、`domain.py:2000`）。前端注释原话——

> `frontend/index.html:5248`：「后端 `open_basis_rate` 目前仍是占位 `"0"`，故用均价现算。」

即：**前端那份 JS 存在的唯一原因，是后端没把这个字段填上。**

### 公式 C —— 发单数量（三处字面重复）

| # | 位置 | 现状 |
|---|---|---|
| 1 | `service.py:3570` | `send_qty = q_common if q_common is not None else D.Decimal(task["single_amount"])` |
| 2 | `live_hedge_executor.py:828` | `send_qty = ctx.q_common if ctx.q_common is not None else ctx.single_amount` |
| 3 | `backend/tests/fakes.py:152` | 与 #2 字面相同 |

三处逻辑相同（`q_common` 为空则回退原始输入），各写各的。

## 3. 改动一：发单数量收敛为一个函数

**改法**：抽 `resolve_send_qty(q_common, single_amount) -> Decimal`，三处共用。

**为什么是纯重构**：三处逻辑本就相同，抽出后行为字面不变。#2/#3 字面完全一致；
#1 多一层 `Decimal(...)` 包装（源为 `task["single_amount"]`，字符串列），
抽出的函数内统一做该转换即可。

**收益**：乘数轮的 §3.1 只需改这一个函数，而不是分别找到三处——r1 正是在这里
只找到了 1/3。`fakes.py` 那份尤其重要：它是假执行器，漏改会让单测两边同错而全绿。

**不在本方案范围**：`q_common is None` 时的拒发判断（那是乘数轮 §3.1 的内容，
本方案不改任何判定，只收敛取值）。

---

## 4. 改动二：后端填 `open_basis_rate`，前端删掉 JS 实现

**改法（关键：就地计算，不走 `cycle_slippage_pct`）**：

在 `aggregate_positions` 内、`spot_avg` / `perp_avg` 算出的**同一处**
（`store.py:2830-2836`），用**同样这两个值**加 `direction` 直接算出 `open_basis_rate`，
替换 `store.py:2860` 的占位 `"0"`；`domain.py:2000` 的占位同步处理。
前端删除 `computeHedgeOpenBasisRate`（`index.html:5249-5259`），改为读取该字段。

**为什么不复用 `cycle_slippage_pct`**（本方案的核心取舍，请评审重点看）：

二者虽公式同形，但**取数口径不同**，直接复用会造成行为变化：

- `aggregate_positions` 的均价分母是 **priced qty**（仅计入 notional 已知的腿），
  并另有 `spot_avg_price_incomplete` / `perp_avg_price_incomplete` 标记；
  全部腿 notional 未知时回退 `0` 并置标记（`store.py:2826-2836` 注释 G5）。
- `cycle_slippage_pct` 在任一腿不可定价或非正时**返回 `None`**（`store.py:2585-2593`）。
- 分桶键也不同：持仓按 `(coin, direction, cycle_id)`；滑点按 `(cycle_id, task_type)`。

→ 复用会让「当前显示数字、但均价不完整」的行下降为 `—`。**那是行为变化，不是重构。**

**就地计算则可证明零行为变化**：输入与前端今天用的是同一对 `spot_avg` / `perp_avg`
和同一个 `direction`，输出必然逐位相同。

**方向口径（须与前端现状逐字对齐）**：

```
forward: (perp_avg − spot_avg) / min(spot_avg, perp_avg)
reverse: (spot_avg − perp_avg) / min(spot_avg, perp_avg)
任一均价 <= 0 或非有限 → 空值（前端现为 NaN → 显示 "—"）
```

**收益**：乘数轮的 §3.5 从三个改动点降为两个，且删掉的是**唯一一个跨语言、
永远无法与后端共享代码**的那份。

**注意**：`frontend/self-check.js:5110-5117` 以硬编码百分比锁死了该公式
（`+0.9868%` / `+0.3210%`）。**这两条断言必须原样继续通过**——它们正是本方案
「零行为变化」的现成证据。

## 5. 明确不做

| 不做 | 理由 |
|---|---|
| 动公式 A（`compute_opening_spread_pct`） | 已是单一共享函数，无重复可合；且是冻结契约、平滑门的资金放行判定 |
| 合并 B 的两份 Python/JS 为「共享实现」 | 跨语言，物理上不可能共享函数。唯一合并方式就是让一边不算——即本方案 |
| 改 `cycle_slippage_pct` | 见 §4，口径不同，动它是行为变化 |
| 任何乘数 / 倍数相关改动 | 属乘数轮（r3），本方案是它的前置，不夹带 |
| 清理 `hedge_open_fill` 死表 | `PROJECT_STATE` 既有 follow-up，涉及生产库 `DROP TABLE`，须 Human 单独授权，**不得夹带** |
| 更广义的「相关业务抽象」 | 范围不可界定，会滚雪球。本方案只收敛两个**已被评审实证漏改**的概念 |

## 6. 验收：零行为变化

两项改动都**不改变任何输出**，因此验收标准是「改前改后完全一致」，不需要新增业务断言：

1. **现有全量测试必须原样通过**，不得修改任何既有断言以适配改动。
   特别是 `frontend/self-check.js:5110-5117` 的两条硬编码百分比。
2. **改动二的等价性证据**：对同一份持仓 fixture，改前（前端算）与改后（后端算）
   渲染出的「开单价差率」列**逐字符相同**，包括 `—` 的情形。
3. **改动一的等价性证据**：三处调用点在 `q_common` 有值与为 `None` 两种输入下，
   取值结果与改前一致。
4. 新增测试仅覆盖**边界**（均价为 0 / 负 / 非有限 → 空值），不新增业务语义。

## 7. 给评审的问题

1. **§4 的「就地计算 vs 复用 `cycle_slippage_pct`」取舍是否正确？**
   本方案主张就地计算，理由是二者取数口径不同（priced qty + incomplete 标记
   vs 返回 `None`；分桶键不同），复用会造成行为变化。请核对该差异是否属实。
   若二者实际等价，则复用是更好的选择，请指出。

2. **§3 的 `resolve_send_qty` 是否真的零行为变化？**
   `service.py:3570` 的 `D.Decimal(task["single_amount"])` 与
   `live_hedge_executor.py:828` / `fakes.py:152` 的 `ctx.single_amount`
   类型是否等价？若 `ctx.single_amount` 已是 `Decimal` 而 task 列是字符串，
   统一转换是否可能改变精度或异常行为？

3. **是否还有第三个「同一概念多处实现」值得一并收敛？**
   请独立搜索。判定标准：该概念已被实证漏改过，或跨语言/跨层重复实现。
   **不要**列出仅仅「看起来可以抽象」的候选——本方案刻意不做广义重构。

4. **§5 的边界是否划得住？** 有无遗漏的、不做会导致本方案不完整的项？

5. **§6 的验收是否足够证明零行为变化？** 特别是改动二，是否存在
   「前端算」与「后端算」在浮点/十进制精度或格式化上产生差异的路径？
   （前端 JS 用 `Number` 浮点，后端 Python 用 `Decimal`。）
