## R4 的新增决议

R3 已通过对正常核验输入、窄写入权限、同文件核验、路径预启动记录、失败降级和归档
终结性的设计审查。R4 只新增并写入以下约束：

- 控制台 `TASK_RESULT v2` 继续保持现有字段和格式，但只能展示交接件中 Human Brief 的
  同格式内容；不得再独立创作控制台叙事。
- Human Brief 与 Source Report 均必须清楚写出下一步的仓库相对文档路径、立即执行动作
  和下一关卡。现有 `下一步任务` 使用：`读取：<paths|none>；执行：<action>；关卡：<gate>`。
- Bookkeeper 核验 Human Brief 与 Source Report 的下一步路径和动作不冲突；该信息不构成
  模型调度授权，也不改变 `status.json` schema。
- 没有终端自动捕获时，不承诺文件简报与控制台文本可逐字比对；仓库内交接件仍是正式原件。

## 审查目标

判断 R4 是否在不改变现有回执字段、Human 启动终端边界、Bookkeeper 单一状态写者和固定
`base_sha..delivery_sha` 审查区间的前提下，使 Human 从控制台回执中直接获得下一文件路径
和执行操作，同时让下一模型能从交接件取得完整上下文。

重点检查：

1. “Human Brief 是控制台回执唯一内容来源”是否与“无终端自动捕获、文件才是正式原件”
   一致，是否仍包含不可机械核验的保证。
2. `下一步任务` 的“读取／执行／关卡”句式是否在保留既有 Task Result 格式的同时足够
   明确；对于无下一文件、Human 决策、REWORK、blocked 与拒收是否都有可执行表达。
3. Human Brief 与 Source Report 的下一步信息双写是否会引入双重权威；Bookkeeper 的
   一致性核验能否把它限定为同一原件内的交叉检查而非新的状态源。
4. R4 是否影响 R3 已通过的正常路径（Human 不复制回执）、`SOURCE_REPORT_MISSING`
   降级、评审者 create-only 权限、同文件 Bookkeeper 核验、预启动路径记录、归档终结性。
5. 是否遗漏实施前必须由 Human 决定的事项。不要提出未被观察到问题的自动捕获器、黑板或
   全量 stage 汇总文件。

## 返回格式

在终端中返回简洁中文评审。开头必须清楚给出且只使用其一：

```text
评审结论: ACCEPT
```

或：

```text
评审结论: REWORK
```

只有不存在实施前未决条件时才能使用 `ACCEPT`。`REWORK` 必须逐项说明：范围分类
（本提案范围内）、问题事实、实际影响、最小可执行修订和对应段落。不要使用
“ACCEPT（附条件）”。

本次为未提交提案的只读复评，Human 会将原始输出转交给提案作者；它不会自行授权实施、
合并、部署或模型调度。
