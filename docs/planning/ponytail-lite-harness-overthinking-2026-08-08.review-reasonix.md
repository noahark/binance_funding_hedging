## 对评审请求八个问题的回答

### Q1 场景准入门是否会压掉必须处理的低概率高损失问题？

**不会整体压掉，但存在一个口子（R1）。** 条件 4（涉及资金、安全、数据损失或缺失关仓
能力，且静态代码路径或控制流能够证明其可达）和 §6 末段（"涉及资金等高风险路径时，不
要求等待真实事故；明确的静态可达路径可以作为证据"）已经给资金类问题留了专用通道，
方向上没有机械忽略。但有两个边界必须钉死：

1. **"静态可达"是资金证据的充分形式，绝不能读成必要条件。** 当前条件 4 的措辞
   （"且静态代码路径或控制流能够证明其可达"）在语法上是进入条件 4 的组成要件，reviewer
   会自然读成"拿不出静态证明就不能提资金问题"。本仓库有现成反例：Live Risks 的划转端点
   R1 和 1000x 腿量换算，最初都是通过**事故分析/审计**识别的，不是先有静态可达证明；
   若严格执行"先证明可达再提"，这些发现会被推迟甚至压掉。修订：把条件 4 改为
   "涉及资金安全清单，且具有**可达性证据**（静态路径、控制流、真实日志/事故样本、或
   无法证明不可达时的 fail-closed 论证，任一即可）"。
2. **"不可达"判定本身是高风险判定，必须与 bStock 先例同规则。** `DEC-2026-08-07-007`
   说明本仓库有"以领域事实证明不可达"的正确先例；但也有过模型因缺该事实而误报的先例。
   因此：**凡是驳回资金清单内场景的"不可达"结论，必须写明判定依据；判定错误的影响方向
   必须 fail-closed**（即拿不准时按可达处理、按非阻塞观察上交 Human，而不是按不可达
   驳回）。这条要在 §4 的"若均不满足"分支里显式写，否则驳回资金类场景没有复审钩子。

### Q2 "静态可达路径即可作为资金风险证据"的边界是否足够明确？

**不够明确（R1 的组成部分）。** 方案没有定义"静态可达"本身：

- 起点是什么？真实入口应限定为：HTTP 端点、worker 轮询循环、任务状态机转换、启动路径、
  外部事件回调。不允许"任何函数都能被调用所以可达"这种泛论。
- 终点是什么？应到"产生实际影响的分支"（写单、划转、改状态、改账、删数据），不是到
  "有一个 if 分支存在"。
- **多前提叠加的判定**：条件 3 用"多个未出现前提同时成立"挡普通场景是对的，但对资金
  场景，方案没有声明"前提数"上限。建议明确：依赖 2 个及以上**独立外部故障/独立配置
  变化**同时成立的组合，除非系统当前已存在该组合状态，否则不算"当前可达"——这是
  "组合性风险"唯一合理的切分线，也符合 §8 验收案例第三行的既有口径。

### Q3 "便宜验证 / fail-closed"是否会反过来成为无限增加检查的借口？

**会，这是本方案最大的自反风险（R2）。** 条件 5"验证或 fail-closed 防护成本很低"的
"成本很低"由模型自评，而本仓库的模型倾向恰恰是把一切风险转成断言/静态检查
（`DEC-2026-07-30-002` 的"not statically defensible"教训就是例子）。必须把条件 5
缩窄：

1. 条件 5 只适用于**验证性断言/测试**，不适用于**新增运行时防御分支、恢复链、新状态、
   新抽象**——防御分支必须走条件 1-4 的准入，不许借"便宜"进入。
2. 每个便宜检查必须能回答"它拦截的具体错误形态"；若说不出的检查不加。
3. 每个便宜检查必须检查自己的误报方向：如果误报（把成功判失败、把正常判异常）会导致
   重发、假暂停或错误状态机转换，则它不是"便宜"，须按条件 4 的 fail-closed 论证重新
   评估。本仓库 money-zero tripwire 的教训（"speed bump, not proof: five evasions"）
   正是这一条的现成教材。

### Q4 Reviewer 的六项证据要求是否过重、重复或仍可被空泛描述绕过？

**不过重、无明显重复，但"可绕过"是真实残余风险（R3 的一部分）。**

- 六项（入口/可达性/前置条件/实际影响/验证 oracle/最小修复边界）对资金路径本来就该
  齐备，对普通功能路径偏重——但方案的目的正是抬高 REWORK 门槛，偏重是设计意图不是缺陷。
- "入口/可达性/前置条件"三者语义有重叠，但保留为独立字段有防绕过价值（让 reviewer
  无法只写"可达"两个字混过去），建议保持，不做合并。
- **真正的可绕过点**：oracle 一项允许"静态控制流证明"，而"证明"可以写成伪证据（引用
  某文件某行却不真的追调用链）。格式本身防不住，需要两条补充：
  1. oracle 必须是**可执行命令、已提交证据路径、或 `文件:行号` 的精确引用**三种之一；
     "代码中有此分支"这类泛述不算。
  2. 六项模板化（固定字段名），并在 reviewer skill 里指向 `AGENTS.md` 而不是在 skill
     里复制字段清单（方案 §7 已如此设计，正确）。

### Q5 是否与现有范围三分类、同根因刹车、Human 风险接受、双评审规则冲突？

**与范围三分类存在一处未声明的优先级冲突（R3），其余兼容。**

- 同根因刹车：兼容。穷举扫描是"任务"，不是"新场景准入"，不经过条件 1-5；方案 §8 案例
  已正确覆盖（"仍执行现有穷举根因扫描，不得用最小修改原则逃避"）。
- Human 风险接受：兼容。§4 末段"反复重提已接受限制"是治理对象，§8 案例有对应行。
- 双评审 / `base_sha..delivery_sha`：兼容，§6 已声明不削弱。
- **冲突点**：范围三分类中 `pre-existing-release-critical`（涉及资金、实盘、账务、安全
  的 pre-existing 发现）"不机械阻塞交付，但阻塞合并/发布"。而 §4 说"不满足任一条件的
  场景不得成为阻塞性评审问题、最多记录非阻塞观察"。二者若在同一个发现上相遇（例如
  reviewer 判定某资金路径"不可达"而驳回，但该判定本身有争议），规则打架：一个说"驳回、
  记观察即可"，一个说"这是合并前 Human 必须决定的具名事项"。修订：在 §4 或 §6 显式
  声明两条门的独立性——**准入门管"REWORK / 实现范围"，范围三分类管"合并发布"**；
  凡命中资金安全清单的驳回/观察，即使不构成 REWORK，也必须按
  `pre-existing-release-critical` 或具名观察上交 Human，不得静默落在"最多记观察"。
  这条同时闭合 R1 的"驳回无复审钩子"问题。

### Q6 三文件范围是否足够？

**主体够，差一处：reviewer skill 的一行提醒是必需的（R4）。**

- `AGENTS.md`（准入 + 证据门）：正确的主权威落点。
- `developer-discipline.md`（决策阶梯 + 验收后停止）：基本合理，但可更小——该文件已有
  "Simplicity First / Surgical Changes / Goal-Driven Execution" 章节，阶梯六步与之
  高度重叠，建议只追加"验收后停止 + 不顺手补建"一句与指向 `AGENTS.md` 的准入引用，
  不整段复制阶梯（符合单一权威原则）。
- `senior-developer.md`（vendored 能力清单定位）：**必要**（我核实其全文确认是重灾区），
  措辞"规模化、熔断、追踪、迁移等是证据触发的能力清单，不是默认交付物"准确。
- 不修改 `software-architect.md` / `task-planner.md`：成立。我核实前者确有"No
  architecture astronautics"等既有约束，后者是 PM 最小化导向文本，无冲突源。
- **缺口**：`code-reviewer.md` 与 `reality-checker.md` 各缺一行提醒。`reality-checker.md`
  全文基调是"Default to finding issues unless proof shows otherwise"——与本次治理的
  痛点（刁钻 REWORK）方向相反；reviewer 加载 skill 时先读到"默认找问题"，再读到
  `AGENTS.md` 的证据门，优先级虽以 `AGENTS.md` 为准，但方案 §7 自设的判据是"缺少提醒
  会导致执行失败"。我认为该判据**成立**：这是痛点来源文件，不是中性文件。建议三文件
  扩为"三文件 + 两个 skill 各一行提醒"（只加"阻塞性发现须满足 `AGENTS.md` 场景准入门
  与证据门"一行，不复制字段清单），不扩大更多范围。

### Q7 哪些文字会被模型误读为"忽略边界场景"或"为了少写代码牺牲正确性"？

1. **条件 4"且静态代码路径或控制流能够证明其可达"** → 误读为"无静态证明不提资金问题"
   （R1，安全反例 1）。
2. **条件 5"验证或 fail-closed 防护成本很低"** → 误读为"便宜检查随便加"（R2）。
3. **§5 阶梯第 6 步"验收通过后停止，不顺手重构或补建未来能力"** → 误读为"验收后看见
   真实缺陷也不报"。须补一句：验收通过后发现真实缺陷必须上报（作为阻塞项或后续项），
   只是不擅自扩大本次范围——与 developer-discipline "If you notice unrelated dead
   code, mention it - don't delete it" 同构。
4. **§9 指标"未经要求新增的抽象、文件和依赖：目标为 0"** → 误读为"任何新文件都是
   失败"。须限定为"实现层的 scope creep"，不含流程性文件（handoff、evidence、dispatch、
   本类评审文档）——否则该指标会与 Task Handoff Evidence Contract 自相矛盾。
5. **§6"单纯的'如果未来……''理论上……'不得构成 REWORK"** → 误读为"凡未发生的都不能
   阻塞"。须显式声明"资金安全例外优先于本条"（§6 末段已有此意，但第一条独立出现时
   容易先被读到）。

### Q8 是否存在更小、同样可验收的整改方案？

**存在，但收益有限，不改变总体形态。** 最小形态可以是：

- 一条准入规则（资金清单 + 证据 OR 关系 + 不可达证明责任在主张方）+ 一个 REWORK 证据
  模板（六字段）+ 试运行，全部落在 `AGENTS.md` 与 `developer-discipline.md` 一句引用。

  的一行提醒不可省（理由见 R4）。这两处省掉就回到"规则正确、执行时被 skill 文本带偏"

- 因此方案已是接近最小的形态；我建议在维持三文件主体的前提下做 R1-R4 修订，而不是另
  起一个更小方案。§9 的试运行（连续 5 个正常任务）保留——它是验证而不是永久合同限额，
  方向正确；唯一修订是指标口径（见 R5）。

## 安全反例

1. **可被压掉的真实资金发现**（R1 口子）：若条件 4 维持"且静态代码路径或控制流能够
   证明其可达"的措辞，一个通过实盘日志/事故样本识别、但尚未补出静态控制流证明的
   资金路径（本仓库划转端点 R1、1000x 腿量换算同型）会被 reviewer 以"证据形式不符"
   挡在准入门之外。后果：资金发现被推迟，且按 §4"最多记非阻塞观察"可能完全消失。
   修订见 R1。
2. **可利用的无限加检查口子**（R2 口子）：条件 5"成本很低"由模型自评，无反向检查，
   模型可以把任何防御分支包装成"便宜 fail-closed"入场（本仓库 `DEC-2026-07-30` 系列
   的断言兜底倾向正是如此）。后果：方案想砍的"防御性膨胀"换个名字回来。修订见 R2。

## 修订要求（REWORK，R1-R5）

- **R1（条件 4 / 资金证据边界）**：把"静态代码路径或控制流能够证明其可达"改为"具有
  可达性证据（静态路径、控制流、真实日志/事故样本、或无法证明不可达时的 fail-closed
  论证，任一即可）"；在 §4"若均不满足"分支追加"驳回资金清单内场景的'不可达'结论必须
  写明判定依据，且拿不准时按可达处理并上交 Human，不得静默驳回"。
- **R2（条件 5 缩窄）**：条件 5 仅适用于验证性断言/测试，不适用于新增运行时防御分支、
  恢复链、新状态、新抽象（后者走条件 1-4）；每个便宜检查须能说明拦截的具体错误形态，
  并检查误报方向（误报若触发重发/假暂停/错误状态转换则须按条件 4 重评）。
- **R3（与范围三分类的优先级）**：在 §4 或 §6 显式声明"准入门管 REWORK/实现范围，范围
  三分类管合并发布"；命中资金安全清单的驳回/观察必须按 `pre-existing-release-critical`
  或具名观察上交 Human，不得静默落为普通观察。
- **R4（文件边界 +1）**：`code-reviewer.md` 与 `reality-checker.md` 的 Project Harness
  Overrides 段各加一行"阻塞性发现须满足 `AGENTS.md` 场景准入门与证据门"；其余文件边界
  维持。同时把 developer-discipline 的拟加内容缩为"验收后停止 + 真实缺陷必须上报"一句
  加指向 `AGENTS.md` 的引用，不整段复制阶梯。
- **R5（试运行指标口径）**：§9"未经要求新增的抽象、文件和依赖：目标为 0"限定为实现层
  scope creep，明确排除流程性文件（handoff/evidence/dispatch/评审文档）；§6"理论上/未来
  不得构成 REWORK"旁注明资金安全例外优先。
