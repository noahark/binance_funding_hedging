# 模型过度思考与刁钻 REWORK 场景治理（Ponytail-lite v2，计划复审稿）

- **日期**：2026-08-08
- **状态**：REWORK 后待独立、跨 provider、只读计划复审
- **风险分类**：HIGH_RISK（Harness 工作流契约拟议变更）
- **权限边界**：本稿只供计划评审，不授权修改 Harness、代码、服务或实盘状态
- **Human 需求**：近一个月约 60% 协作时间消耗在 Human 估计发生概率低于 1% 的刁钻场景；该比例是经验估计，不是统计测量

---

## 1. v2 结论

不安装 Ponytail，不替换 `software-architect.md`，不新增 skill、角色、状态字段、verdict、计数器或统一概率阈值。只吸收三点：

1. 新场景先证明当前相关性，再允许扩大范围或 `REWORK`；
2. 先复用现有权威路径，以最小、清晰、可审计的改动完成验收后停止；
3. 把 `senior-developer.md` 中规模化能力从默认要求降为证据触发的参考能力。

治理对象是**模型自行提出的新假设场景**，不是需求、验收标准、已观察缺陷或缺失的必需证据。资金安全、数据损失、关仓能力和信任边界不得因低概率而被忽略。

## 2. v1 评审后的收编与驳回

已收编四份评审的共同意见：

- “便宜验证”不能独立让新场景入场；
- 资金风险的可达性凭据不限于静态调用链；
- 准入门不能覆盖已复现缺陷、验收失败、需求不符或必要证据缺失；
- 准入门不改变范围三分类、同根因刹车、Human 风险接受和双评审；
- 新规则并入现有权威，不复制一套完整阶梯或六字段表格；
- `senior-developer.md` 的 vendored 规模化默认倾向是最高杠杆整改点。

本版明确不采用：

- 给 Bookkeeper 扩展技术评审裁决权或把 reviewer finding 纳入 `contested`；
- “三文件净字节必须小于等于零”等文本体积硬指标；
- 把每个被驳回场景写入 `PROJECT_STATE.md` 的永久账本；
- 修改 `code-reviewer.md`、`reality-checker.md` 或其他 reviewer skill；
- 强制所有问题填写六项散文字段；
- 把当前单进程、SQLite、端口等易变化事实固化进通用 skill；
- 对非阻塞观察不设数量上限。

若复审认为上述任一驳回会造成现实安全缺口，须给出当前仓库中的具体反例和更小替代方案。

## 3. 场景准入：拟写入 `AGENTS.md` §1 的执行口径

现有 §1 已是“只解决有证据的问题，并保留资金安全例外”的唯一通用权威。v2 只在该处补充执行口径，不另建第二份例外清单。

需求、验收标准、已观察缺陷、测试失败、需求不符或交付缺失必需证据不属于“新假设”，直接按现有规则处理。除此之外，模型自行提出的新假设场景只有满足以下任一条件，才可扩大当前实现范围或成为阻塞性评审发现：

1. **当前可达**：有具体的当前入口、前置条件和实际影响，并至少有一项可核验凭据；
2. **高损失例外**：命中 `AGENTS.md` 既有资金、安全、数据损失、缺失关仓等保留项，且至少有一个当前存在的前提和一项可核验凭据；不要求事故已经发生，也不要求先补出完整静态调用链。

可核验凭据按问题形状选择，可以是：

- 可执行测试或命令；
- 原始日志、样本或已提交证据路径；
- 支撑主张的 `文件:行号` 与可追踪控制流；
- 正式外部契约或交易所文档允许的事件/返回值；
- 已记录的领域事实或 Human 固定前提；
- 并发问题的两个真实入口、共享可变状态和缺少互斥的论证；
- omission（缺失能力）的外部可发生事件和我方缺少接收/处置分支的证明；
- 同一 stage 内由当前验收标准连接的接口或契约不一致；
- 资金单位、精度、倍率或取整公式的直接推导与样本。

仅写“理论上可能”“未来可能”“代码里有这个分支”不构成凭据。反过来，仅写“没找到调用方”也不能证明资金路径不可达；驳回资金类场景须给出领域事实、固定前提、命令、样本或代码证据。若已有至少一项具体凭据指向当前资金影响，但整体可达性仍无法证实或证伪，作为具名事项上交 Human，不得静默丢弃，也不得直接 `REWORK`。

未通过准入的新假设场景：

- 不修改交付，不扩大文件或契约范围，不发出 `REWORK`；
- 一般不进入给 Human 的摘要；
- 只有预计会反复出现且能写出明确重开触发条件时，才在本次评审证据中留一行非阻塞观察；
- 只有 Human 确认其为跨阶段领域事实、固定运行前提或已接受风险时，才进入现有持久权威；不新建排除场景账本。

这些不属于新假设的失败继续按现有 fail-closed 规则处理，不能因准入门而变成 `ACCEPT`。

## 4. “便宜验证”的收窄

“便宜”不能独立让一个新场景通过准入门。只有场景已由第 3 节的条件 1–2 准入后，才可以选择现有结构内的最小验证。

若验证需要新增运行状态、错误类别、暂停原因、恢复动作、公共契约、配置、依赖、抽象，或带来新的运维处置义务，就不属于便宜验证，必须按正常任务重新判断范围。

断言或测试必须说明保护的具名不变量和误报方向；断言是防回归护栏，不是完整正确性证明。无人读取、没有处置动作的新增日志也不算 fail-closed。

## 5. 正式评审执行口径：拟写入 `AGENTS.md` §8

只有 Reviewer 用**自行提出的新假设场景**阻塞交付时，才适用场景准入和新增凭据要求。该发现至少要提供：

- 一项与主张相匹配的可核验凭据；
- 对当前交付的具体影响；
- 为什么必须在本轮修，而不是带重开条件的后续观察。

不要求机械填写六字段模板。已有失败测试、原始证据或验收失败的问题继续直接按现有评审规则处理。

准入门只决定当前实现范围和 `REWORK`；现有发现范围三分类继续决定交付、合并和发布路径。`pre-existing-release-critical` 的 Human 上交通道不受影响。同根因刹车触发后的穷举扫描是已授权范围，不要求每个站点重新通过场景准入。

不扩展 `contested`，不授权 Bookkeeper 覆盖 Reviewer 的正式 verdict。无明确 `ACCEPT` 仍然非接受；证据不合规的评审回执不能被 Bookkeeper 自行改成接受。

## 6. 实现纪律：拟并入 `developer-discipline.md` 现有章节

不复制完整 Ponytail 阶梯，只补当前文件缺少的三点：

1. 写新代码前，先查找已有权威模块、数据源、执行路径或共享根因；
2. 验收标准和所需测试通过后停止扩张，不顺手补建未来能力；此后发现真实缺陷仍须报告，只是不擅自夹带实现；
3. `AGENTS.md` 同根因刹车要求的穷举扫描属于明确授权范围，不受“停止扩张”限制。

不引入“一行优先”、代码行数配额或统一依赖优先级。资金数量、单位、精度、取整、部分成功、未知状态、关仓能力、审计证据和信任边界输入验证不以减少代码为目标。

## 7. 实现 skill 降权：拟修改 `senior-developer.md` Overrides

只在顶部 Project Harness Overrides 增加一条高优先级规则：

> `developer-discipline.md` 是本项目实现简洁性的详细权威。下方 vendored 文本中的规模化、微服务、熔断、隔舱、死信队列、分布式追踪、SLO、零停机迁移等是参考能力，不是默认交付物；仅在 dispatch、已观察故障、测量数据或当前验收明确要求时适用。

不修改 vendored provenance，不在 skill 中复制场景准入条件或资金安全清单，也不写死当前部署形态。

## 9. 计划验收案例

| 场景 | 预期处理 |
|---|---|
| 已有测试或日志复现普通缺陷 | 不适用新场景门，直接按现有规则处理 |
| 静态可达的订单、持仓、划转或无法关仓风险 | 有当前前提和凭据即可阻塞，不等待事故 |
| 两个真实并发入口共享可变资金状态且无互斥 | 并发论证构成可达性凭据 |
| 交易所正式契约允许某失败/部分成功事件，而我方缺少处置分支 | omission 证明构成凭据 |
| 同一 stage 内前后端接口不一致 | 按验收标准处理，不适用新场景门 |
| 单位、倍率、精度或取整方向可直接推导错误 | 命中资金语义，可阻塞 |
| 多个未出现前提叠加、无当前入口或凭据的普通场景 | 不扩范围、不 `REWORK`、不进 Human 摘要 |
| Human 已接受的限制且前提未变化 | 引用现有决定，不重复阻塞 |
| 新场景只因为“加一个检查很便宜” | 不能入场；cheap-check 不是准入理由 |
| 已准入场景可由现有测试内一个不变量断言防回归 | 可以增加，但不得把断言当完整证明 |
| Reviewer 以新假设场景阻塞但只写泛泛散文 | 不满足凭据要求 |
| 交付缺少必需证据或验收失败 | 继续非接受，不得用新场景门放行 |
| 连续两轮同根因 `REWORK` | 执行既有穷举扫描，不逐站点重过准入门 |
| 至少一项具体凭据指向当前资金影响，但整体可达性暂时无法证实或证伪 | 具名上交 Human；不静默丢弃、不直接 `REWORK` |

## 10. 试运行

正式实施完成 review-1、review-2 并经 Human 启用后，再用连续 5 个正常任务观察行为；该数量不是永久合同限额，也不用于统计证明低概率资金风险安全。

试运行同时运行第 9 节确定性案例，观察：

- 给 Human 的摘要中未通过准入的假设场景数量为 0；
- 每条由新假设场景产生的 `REWORK` 都有可核验凭据和当前影响；
- 没有未经准入产生的实现层抽象、依赖、配置、状态或恢复链；
- Human 感受到的假设场景讨论耗时从当前估计约 60% 至少降低一半；
- 若任何资金缺陷因准入门被错误放行并进入合并，立即停止试运行，恢复试运行前行为并重新设计。

流程性 handoff、evidence、dispatch 和评审文档不计入“未经要求新增实现文件”。试运行结论不能替代正式安全评审或 Human 决策。
