## 二、对六个问题的回答

### Q1 v2 是否仍可能压掉真实低概率高损失问题？

**总体显著好于 v1**（条件 2 不再要求完整静态调用链、驳回方需举证、新增"具名上交 Human"通道、四类特殊凭据形式全部收编）。但有两个当前可达的缺口：

**安全反例 A：分类下压。** §3 对*驳回资金类场景*设了举证义务，但对**"这不算资金类"这一步分类本身**没有任何义务。分类是准入判断的第一步，因此举证义务可被一次无成本的降级绕过。
当前先例：`PROJECT_STATE.md` Live Risks 明确记载"持仓表 `single_leg_exposure` 对乘数币因量纲不同会误报"，Current Status 记载 X/Y/Z 数量口径争议——**敞口数字显示错误**究竟算"展示问题"还是"账务含义/资金语义"，本仓库真实存在这种模糊。评审者只要归入前者，§3 的举证要求就不适用，可以不提也不必说明理由。
→ **C2**：§3 追加"**是否命中资金安全保留项本身存疑时，按高损失例外处理**"。与 §3 已有的"可达性存疑上交 Human"完全对称，一句话。

**安全反例 B：评审者结构上取不到凭据的资金场景，v2 给它的通道比 v1 更窄。** §3 规定未准入场景"只有预计会**反复出现**且能写出重开触发条件时，才留一行非阻塞观察"。而评审者是只读会话（`AGENTS.md` §3.4/§3.6、`roles.md` Reviewer Isolation），**不能查交易所、不能读实盘账户状态、不能调 API**。因此凡凭据必须来自当前账户或平台状态的资金场景，评审者结构上取不到凭据；若它又不是"预计反复出现"的类型，v2 下的正确行为是**静默丢弃**——v1 至少还允许记一行观察。
当前先例形状：51169 平台级抵押额度打满（全平台共用、无 API 可读、会自行解封）——正是"评审者无法取证、但真实导致过合约腿成交而现货腿被拒的裸空"的那一类。
→ **C3**：§3 修为"触及资金安全保留项的场景，即使暂无充分凭据，也可在**评审证据**中留一行（不进 Human 摘要），不受'预计反复出现'限制"。成本是评审证据里多几行，不占 Human 时间。

覆盖矩阵（修订后第三行才被填上）：

| 情形 | v2 现文字 | C2/C3 后 |
|---|---|---|
| 有凭据 + 可达 | 阻塞 ✓ | 同 |
| 有凭据 + 资金 + 可达性不明 | 具名上交 Human ✓ | 同 |
| **无充分凭据 + 触及资金保留项** | **无通道，静默丢弃 ⚠** | 评审证据一行观察 ✓ |
| 无凭据 + 普通 + 会复发 | 一行观察 ✓ | 同 |
| 无凭据 + 普通 + 不复发 | 丢弃 ✓（设计意图） | 同 |

### Q2 哪条文字仍可能被用来扩大范围或制造 REWORK？

**最主要的残留：条件 2 对本仓库近乎全覆盖。** §3 条件 2 要求"命中保留项 + **至少一个当前存在的前提** + 一项可核验凭据"。本仓库大部分代码与资金相邻，"系统当前会下单/会划转"这类前提永远成立；凭据里的"`文件:行号` 与可追踪控制流"对任何已存在分支都能产出。v2 已用"仅写'代码里有这个分支'不构成凭据"堵了最粗的口子（这句很关键，务必保留原样），但**门在资金场景上仍然只是薄薄一层**。

这不是缺陷，是"低概率高损失不得忽略"的必然代价。真正的影响是**预期效果**：门会明显约束普通场景，而在资金场景上几乎不咬合——如果 Human 感受到的 60% 恰好集中在资金场景（本仓库的性质使这很可能），实际降幅会显著低于预期。
→ **不建议改文字**（改了就会压掉真发现），建议改试运行的观测项：**记录每条准入发现是走条件 1 还是条件 2**。这是唯一能在 5 个任务内便宜地看出"门是否咬住"的信号，比"耗时是否减半"的主观感受可测得多。

次要两处：

1. **§3"一般不进入给 Human 的摘要"中的"一般"**——合同里的"一般"等于模型自由裁量，而 §10 把它当**硬指标**测（"未通过准入的假设场景数量为 0"）。**同一份文件的两节互相矛盾。** → **C1**：删"一般"，唯一例外沿用已定义的"具名上交 Human"。
2. **§4 的作用域可能被读反。** §4 说"只有场景经条件 1–2 准入后，才可以选择最小验证"。实现者写新代码时正常需要的输入校验、不变量断言与测试**不是**在处理"新假设场景"，但 §4 的标题与措辞会让人以为断言都要先过门。护栏其实在 §6（"信任边界输入验证不以减少代码为目标"），但在另一节。→ 建议（非阻塞）：§4 加半句"本节只约束为新假设场景增加的验证；实现自身需要的输入校验、不变量与测试见 §6"。

### Q3 不扩展 `contested`、不建账本、暂不改 reviewer skills，是否有现实工作流缺口？

**账本与 reviewer skills：无缺口**（理由见第一节，各补一句即可）：

- 账本：明确模型可在报告中**提议**"某场景应作为领域事实/固定前提记入现有持久权威"，由 Human 确认。否则该通道永远无人发起。
- reviewer skills：§10 加一条观察项——"评审者是否以 skill 文本（如 `reality-checker.md` 的 `Default to finding issues unless proof shows otherwise`）对抗 §1 准入"。v2 §8 的触发式处理是对的，但触发信号必须有人看。

**`contested`：有一个窄缺口，但我不再主张用 `contested` 补。** 缺口是：门约束的是"评审者写什么"，一旦不合规的 `REWORK` 已经发出，合同里**没有比走完整修复轮更便宜的出路**——`AGENTS.md` §8 规定"凡为响应评审发现而改动…一律递增 `rework_count`"，于是不合规发现照样吃掉 3 轮预算中的 1 轮，把交付推向"Human 越门验收"。这不是假设：`hedge-order-truth-v1` 七轮 review-1 终局就是 Human 显式越门验收。

**更小替代（只改计数，不改任何权限）**：`AGENTS.md` §8 加一句——**由 Human 认定为不满足 §1 准入的发现所触发的修复轮，不递增 `rework_count`**。这与既有豁免同构（"缺陷在 packet 不在交付"，此处是"缺陷在发现不在交付"），不扩展 `contested`、不给 Bookkeeper 任何裁决权、不新增字段或枚举。
**列为可选**：它只减轻压力、不改变行为，v2 若认为多一句不值，我不坚持。

### Q4 三文件范围与单一权威安排是否成立？

**成立。**逐条核过：准入口径落在 `AGENTS.md` §1（§1 本就是"只解决有证据的问题 + 保留资金安全例外"的唯一通用权威）；评审执行口径落在 §8（Review Rules 的既有权威）；`developer-discipline.md` 只补三点、不复制阶梯；`senior-developer.md` 只加指针、明确不复制准入条件与资金安全清单，且不写死部署形态——**这一点 v2 比我 v1 的建议更对**：我原本要把"单进程 / SQLite / `127.0.0.1:8787`"写进通用 skill，那是把易变事实固化进长寿文件，v2 拒绝正确。

两处 §2 单一权威的小瑕疵（建议顺手修，非阻塞）：

1. §5 重述了"一项与主张相匹配的可核验凭据"，而该要求的权威在 §3。改为引用 §1 准入的凭据要求即可。
2. §3 的凭据清单 9 条是示例，但**没有一句话说明它是示例**。模型读到 9 条 bullet 会按穷举清单执行，一个凭据形状不在列内的真实发现会被判"形式不符"。→ **C4**：加"本清单为示例，不穷举；凭据只需与主张的形状相匹配"。顺带把 9 条压到 3 行（并发/omission/单位精度三类保留具名，其余归并），少占每次启动的上下文。

### Q5 第 9 节案例能否区分真实发现与无证据假设？缺哪个关键案例？

能区分大部分。**结构性缺口：14 个案例全部是"提出场景"方向，没有一个是"驳回/分类"方向**——即案例表只单向测试了这道门。这正好对应安全反例 A、B。建议新增 4 例：

| 场景 | 预期处理 |
|---|---|
| 以"没找到调用方"驳回一个资金类场景 | 不成立；须给领域事实、固定前提、命令、样本或代码证据（对应 §3 已有文字，但表里无案例） |
| 场景是否命中资金安全保留项本身存疑 | 按高损失例外处理（C2） |
| 触及资金保留项，但凭据须来自评审者取不到的交易所/账户状态 | 允许在评审证据留一行观察，不受"预计反复出现"限制；不得静默丢弃（C3） |
| 真实缺陷的凭据形状不在 §3 示例清单内 | 清单为示例非穷举，形状匹配即可（C4） |

### Q6 是否存在更小且同样安全的修改？

**v2 已接近最小，我不提出替代方案。**三处可再瘦身，合计约减 8 行常驻启动文字，且都是 §2 单一权威的直接要求：①凭据清单 9 条 → 3 行 + "示例非穷举"（C4 同一处）；②§5 引用而非重述凭据要求；③§3"一般不"→"不"（C1，顺带消除与 §10 的矛盾）。

若 Human 希望进一步降低风险敞口，可作为**退路**（我不推荐主动拆）：§7（`senior-developer.md` 降权，1 段）与 §6（`developer-discipline.md` 3 点）零误读风险、且命中的是每个实现任务都在加载的最大反向文本压力；§3/§5 承载了本方案几乎全部残留误读风险。若实现 stage 在评审中卡住，先落 §7+§6 是安全的部分交付。**但拆分会丢掉 reviewer 侧收益，而 Q2 分析显示 reviewer 侧正是 60% 的主要来源之一，故整包交付更优。**
