## 对三处驳回的独立判断

**驳回 1（不加 reviewer skill 提醒）——成立。** opus5 与本人都不赞成 reasonix R4：`AGENTS.md`
是启动第 1 读物、评审者必读，再加指针违反 §2 单一权威；更关键的是 opus5 指出的——在
`reality-checker.md`"Default to finding issues"那句反向话**旁边**加一行正向提醒，得到两条
方向相反的并列指令，比只有任一条都糟。v2 改用 §3/§5 的消歧句（"不属于新假设的失败继续按
现有 fail-closed 规则处理"）替代，成本更低、更不易被临时挑读。正确。

**驳回 2（不设净字节硬指标）——成立。** opus5 P2 有两层：(a) 启动上下文已超 8K 预算，新规则
在 token 第 15K 处对抗第 2.8K 处的 vendored 文本，位置越靠后越弱；(b) 治理"少写"的合同自己
应当 wc -c ≤0。v2 驳回的是 (b) 这个硬指标，但**实质回应了 (a)**：准入门放 §1（启动最前、
最高优先级，位置正确），senior-dev §7 降权直接削弱那 2.8K 的反向压力。按 opus5 自己估算，
senior-dev 降权释放的字节已"抵掉新增文字有余"，硬指标在此冗余。唯一要观察的是 opus5 的
真实担忧——"一句话能不能压住 230 行 vendored 指令"——这是经验问题，留给试运行，且 v2 §8
已留了"试运行证明某 skill 持续覆盖上位规则则另开任务"的升级口。可接受。

**驳回 3（不扩展 contested）——成立。** opus5 P4 的担心真实：证据门是可争辩判断，无仲裁者
时实现者反驳→评审者再主张→Human 裁决，Human 耗时反升。但把 `contested` 扩展到"评审发现"
会让 Bookkeeper（状态核验角色）去裁定**技术证据争议**，模糊 §3 Safety Kernel 的"评审者是
技术权威、Bookkeeper 不覆盖 verdict"边界；且 opus5 自己的护栏"资金类争议上交 Human"说明，
在高损失场景 Human 本就是终审——contested 扩展只对低损失争议省一轮修复，收益边际。

v2 的替代执行链是：**评审者按 §5 自律（必读 §8）→ HIGH_RISK 的 review-2 做 evidence 复核 →
`rework_count` 上限 3 → Human 裁决**。一个证据不足的 REWORK 最坏代价是烧掉一轮修复 + 一次
计数，触及上限即由 Human 决定。这是有界回退，且与方案"不新增机制/字段/角色"的非目标一致。
**唯一残余**：证据不足的 REWORK 在被纠正前仍会强制一轮修复、消耗预算——这是效率残余不是安全
残余，建议试运行专门追踪"滑过证据门的 REWORK 条数"（见次要备注 2）。

## 对 v2 §11 六个问题的回答

### Q1 v2 是否仍可能压掉真实低概率高损失问题？

**不会。** 我试图构造反例，逐一被 §3 条件 2 + 凭据清单 + 末段对称举证挡回：

- 多前提叠加的资金风险（部分成交 × webhook 延迟 × DB 重试）：条件 2 只要"≥1 当前前提 + ≥1
  凭据"，不要求所有前提都证。一条腿可证即放行——这正是放行"低概率高损失"的设计意图。
- omission 类（缺关仓分支）：凭据清单明列"外部可发生事件 + 我方缺少接收/处置分支"。
- 取整/单位错误：凭据清单明列"资金单位/精度/倍率/取整公式的直接推导与样本"。
- 证不到的资金路径：§3 末段 + §9 行 14"上交 Human，不静默丢弃"。

唯一仍需 Human 决策前由 Planner 钉一句的：§3 条件 1（非资金）要求"具体当前入口、前置条件、
实际影响"全列、但"≥1 凭据"可只背书其中一条——理论上可拿一条无关 file:line 凑数。条件 2
（资金）的这种放松是**安全方向**（放行更多资金发现），条件 1（非资金）则应要求凭据背书
**承载性前提**而非任一前提。这不是安全反例，是防作弊的措辞精度，见次要备注 3。

### Q2 哪条准入文字仍可能让模型用刁钻假设扩大范围或制造 REWORK？

主要残余在 §3 凭据清单的"支撑主张的 `文件:行号` 与可追踪控制流"——一个真实存在的 file:line
可被夸大为场景的入口，而触发所需的其他前提当前并不成立。这是任何证据门的固有面，无法靠加
字段消除（opus5 Q4 同判）。v2 的二次防线"对当前交付的具体影响 + 为什么必须在本轮修"能挡掉
大部分，残留交试运行观察。属可接受的残余，非阻塞。

### Q3 不扩展 contested、不建排除账本、暂不改 reviewer skills 是否有现实工作流缺口？

**无安全缺口；有一处效率缺口（见"唯一建议"）。** 执行链（§5 自律 → review-2 → rework_count
上限 → Human）对安全充分。不扩展 contested 保住了权威边界（见驳回 3）。不改 reviewer skills
用消歧句替代（见驳回 1）。唯一缺口是跨阶段去重——见下。

### Q4 三文件范围与单一权威是否成立？

**成立。** §3 落 §1（既有原则的执行口径，非新章节）、§5 落 §8（既有 Review Rules）、§6 补
discipline 现文件缺的三条（非平行阶梯）、§7 一条 override 指向 discipline（不复制规则）。
无新文件、无重复权威。§1（实现侧准入）+ §8（评审侧证据门）的切分与既有 §1/§8 分工同构。

### Q5 §9 案例能否区分"真实安全发现"与"无证据假设"？缺哪个关键案例？

**能。** 14 行覆盖了并发、omission、seam、取整、cheap-check 走私、泛泛散文、验收失败不放行、
同根因扫描、证不到的资金路径上交——区分度高。建议可选补一条（次要备注 3）：测"有真实
file:line 但触发前提当前不成立"的非资金场景应判非阻塞，把"当前可达"的"当前"钉死。

### Q6 是否存在更小且同样安全、可验收的修改？

**没有实质更小的了。** v2 已在 Alt B 形态。§3 凭据清单的 9 类是正面定义，砍任何一类都会让
门更易误拒真实证据（与安全反向），不能砍。§6 三条 bullet 各有去重/防误读职责，砍不掉。§7
已是一条 override。唯一可议是 §9 案例表能否再压，但那是排版不是结构。v2 已在膝点。

## 唯一建议（非阻塞）：补回 opus5 P5 的跨阶段去重

v2 §2 驳回"把每个被驳回场景写入 PROJECT_STATE.md 的永久账本"——若指"每条拒绝都记账"，驳回
正确。但 opus5 P5 的实际提议不是这个：它是在**既有 PROJECT_STATE.md** 追加一行"事实 + 排除
依据 + **重开触发条件**"（仓库已有 `BY-DESIGN / Standing operating premise`、`DEC-2026-08-07-007`
bStock 无借币市场等同款写法），不是新建账本、不是永久——每条带重开触发，前提变了就自动重开。

问题在于：评审是全新只读会话，**只读 PROJECT_STATE.md + 当前 packet，不读历史 stage 的评审
证据**。v2 §3 ¶4 把"预计会反复出现的非阻塞观察"放在"本次评审证据"里——这是 stage 局部的，
下一个 stage 的新评审者看不到，于是同一批假设在 2-3 个 stage 后回流，60% 原地不动。这直接
削弱方案自设的"耗时减半"指标。

**建议（合成本人 + opus5，零新机制）**：把 v2 §3 ¶4 那句"只有预计会反复出现且能写出明确重开
触发条件时，才在本次评审证据中留一行非阻塞观察"的范围，从"本次评审证据"改为"**PROJECT_STATE.md
一行 + 本次评审证据**"——即：评审者判定某被拒假设"预计会反复出现"且能写出重开触发时，既
留评审证据，也在既有 PROJECT_STATE.md 追加一行（事实 + 排除依据 + 重开触发）。不新建账本
（复用既有文件既有写法）、不需 Human 逐条确认（重开触发是安全阀）、不需 contested（评审者
自行判断"预计会反复出现"）。Human 若不同意某条，可在读 PROJECT_STATE.md 时撤销——这与既有
accepted-risk 条目的管理方式一致。

这一条不改 ACCEPT 结论；Planner 可在定稿时一句话扩 §3 ¶4 的落点，或显式选择"留给试运行验证
回流是否真发生再决定"。我倾向前者——它是方案里**唯一会随时间变便宜**的机制，早加早受益。
