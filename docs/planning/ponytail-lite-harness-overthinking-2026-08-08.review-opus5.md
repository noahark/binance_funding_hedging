## 总体判断

**问题诊断准确，方向正确，但解法的形状与问题的形状不匹配。**

方案把"过度思考"当成一个**规则缺失**问题来治（加准入门、加证据要求、加阶梯）。但从我核实的仓库实情看，它主要是一个**注意力预算与文本压力**问题：

1. **`senior-developer.md` 是过度思考的文本源，而方案给它的处方太轻。** 我通读全文确认（与 reasonix 同判）：这是 vendored 的 Backend Architect 角色，通篇 circuit breakers / bulkheads / DLQ / 分布式追踪 / SLO / 多区域复制 / 零停机迁移 / "**Default requirement**: Include comprehensive security measures and monitoring in all systems" / "You're successful when... system successfully handles 10x normal traffic"。而 `agents/roles.md:226` 规定 Implementer **每次实现任务都必须加载它**（Shared Rules: Implementer dispatch names exactly one skill）。也就是说，Harness 目前在每一个实现任务里主动提示模型过度建设，约 2.8K token（粗算）。方案的处方是加一句"这些是证据触发的能力清单"——**一句话对抗 230 行反向指令，会输。**

2. **加规则不是免费的。** `AGENTS.md` §4 自设"启动约 8K token、加载任务约 15K"。实测粗算：`AGENTS.md` ≈4.6K + `PROJECT_STATE.md` ≈6.5K（二者均为强制启动读物）+ dispatch + `status.json` + roles 章节 + skill ≈ 13-15K，**启动已约 2 倍超预算**。再加 40-60 行合同文字，新规则将在上下文第 15K 处生效，去对抗第 2.8K 处读到的 vendored 指令。位置越靠后、越抽象的规则越容易被忽略——这是本方案最可能的失败方式，不是文字不对。

3. **因此最高杠杆的改动是删/降权，不是增。** 一个可核验的验收标准：**三文件改动后 `wc -c` 净增 ≤ 0**。把 vendored 正文默认降权（一句话）释放的预算，远大于准入门需要的十几行。一个治理"少写"的合同，自己应当先做到少写。

4. 方案的自我克制正确且应保留：不设概率阈值、不引入 lite/full/ultra、不新增 verdict/字段/角色/计数器、不做代码行数指标。这四条我完全赞同，无修改建议。

5. 一个事实观察（非指责）：这份 10KB 的评审稿 + reasonix 的 268 行 + 本文，是"治理过度思考"这件事本身已经消耗的散文量。**这正是 P1 的实证**——耗时不在 REWORK 路径上，在散文上。

## 对八个问题的回答

### Q1 准入门是否会压掉必须处理的低概率高损失问题？

**会，有四类**（reasonix 的 R1 讲的是"证据形式"被卡；我讲的是**结构上无法表达**，两者不同）。条件 3/4 要求"完整可达路径：前置状态、入口、关键分支、触发输入"。以下四类缺陷天然没有这种形状：

1. **并发交错。** 竞态的"前置条件"是时序，不是状态；静态控制流不证明交错。仓库先例：`PROJECT_STATE.md` Operating Limits `[OPEN][ACCEPTED] F1-P1`——worker handoff 会清掉重入 worker 的重试计数器，窗口毫秒级。它是**先被发现命名、再被 Human 接受**的；按新门，一个只能说"共享可变状态无互斥 + 两个已存在入口"的评审者拿不出"触发输入"，会被驳。
   → 需明确：**"命名两个已存在的并发入口 + 无互斥保护的共享可变状态"本身即构成可达性证据，不要求交错轨迹。**
2. **缺失能力（errors of omission）。** 代码不存在，就没有路径可展示。而这恰是本仓库最大的资金风险形态：一腿成交、另一腿被拒 → 裸露敞口（`PROJECT_STATE.md` regular-spot 路由条：`-2015` → `LEG_UNKNOWN_QUERYING` → 暂停，而并发的 PAPI UM SELL 可能已成交）。
   → 需明确：**对 omission，"路径" = 交易所/领域已文档化会产生的外部事件 + 我方接收它的分支；外部半段以交易所行为文档为证即可。**
3. **跨终端 seam 漂移。** 后端交付一半、前端另一半时，漂移在当前代码里"不可达"（另一半还没并）。仓库有连抓 3 次的记录（`hedge-open-live-v1`）。
   → 需明确：**同一 stage 内将被消费的接口/契约不一致，按本次验收标准处理，不走可达性证明。**
4. **单位/精度/取整方向。** 方案 §5 已把它们排除在"代码量删减"之外，但 §4 的准入门**没有**把它们排除在"可达性举证"之外。取整方向错误在触发前没有"触发输入"。
   → 需明确：这几项直接落在资金安全清单里（现文字"资金…账务含义"或可涵盖，但既然 §5 已单列，§4 应同样单列，避免读者认为两处有意不同）。

另确认 reasonix R1 成立：条件 4 的"**且**静态代码路径…能够证明其可达"在语法上是必要条件，会卡掉以实盘日志/审计识别、尚无静态证明的资金发现。

### Q2 "静态可达即资金证据"的边界是否足够明确？

**不明确，且我认为需要的是"举证责任对称"，而不只是把定义写细。**

- 定义层面赞同 reasonix：起点限定为真实入口（HTTP 路由 / worker 轮询 / 状态机转换 / 启动路径 / 外部回调），终点限定为**产生实际影响的分支**（下单、划转、改状态、改账、删数据），不接受"任何函数都能被调用所以可达"。
- 我要补的是**非对称性风险**：方案让评审者为"挡"付出六项证据，却让"驳"免费。在一个实现者与评审者跨 provider、评审者是安全网的系统里，单方面抬高安全网的成本，均衡点会移向**少挡**。
  → 需写死：**驳回资金安全清单内的场景，必须给出与主张同等形式的凭据**（`文件:行号`、可执行命令、样本、或已记录的领域事实如 `DEC-2026-08-07-007` bStock 无借币市场）。拿不准按可达处理并上交 Human。
- 另一条硬边界（reasonix Q2 提到组合数，我给不同切法）：前提中若包含**已被 Human 声明为固定的配置**（如 `PROJECT_STATE.md` 中"生产 API key、IP 白名单、账户权限固定"这条 accepted-configuration-risk），该场景不算当前可达——**除非该前提本身改变**。这比数"几个前提"更可执行，且直接复用已有记录。

### Q3 "便宜验证 / fail-closed"会否成为无限加检查的借口？

**会。**赞同 reasonix R2 的全部三条收窄，不复述。补两点：

1. **"便宜"必须定义为运行期与运维期便宜，不是打字便宜。** 本仓库的 pause reason / signal 是一套词汇（`PAUSE_REASON_SPOT_ROUTE_CHANGED` 等）；新增一个暂停原因就是契约变更，不是便宜检查。判据：**若该检查触发时需要新的状态、新的暂停原因、新的错误类或新的恢复动作，它不便宜**，走条件 1-4。
2. 仓库已有现成教材，建议在合同里直接引用：`DEC-2026-07-30-001` 的 money-zero tripwire——"**a speed bump against accidental reintroduction, not a proof**"，五种已知绕过。**断言不是证明**这句话本身就该进合同，它同时防住"用断言兜底一切"和"因为有断言所以不用想"两个方向。

### Q4 六项证据要求是否过重、重复或可被绕过？

**这是我与 reasonix 的第二处分歧。它说"不过重、保持六项"；我说六项的过滤方向是反的。**

- LLM 极擅长写出六段自信的散文。**字段数过滤不掉自信的错误发现，只过滤掉懒惰的正确发现**——一个评审者面对六字段税，要么写满（成本转嫁给 Human 阅读，即 P1），要么把真发现降级成非阻塞观察以避税。后者是危险失败。
- 真正的过滤器只有一个：**至少一项机器可核验凭据**——可执行命令 / 已提交证据路径 / `文件:行号` 精确引用 / `git blame` 引用，四选一。这一条能替掉六项里的五项，且**无法用散文绕过**。reasonix 的 Q4.1 已摸到 oracle 这一点，我主张把它从"六项之一的补充要求"升级为"**唯一的硬门**"，其余五项降为写作指引。
- **另有一处方案自身的范围不一致，必须修**：§6 正文说的是"Reviewer 若要用一个**新场景**阻塞交付"，但 §7 文件表写的是"在 Review Rules 中要求**阻塞问题**满足证据门"。后者若原样落进 `AGENTS.md`，**每一条普通缺陷发现**（测试挂了、符号反了、单位错了）都要付六字段税。必须统一为：**本门只约束"模型自行提出的新假设场景"，不约束有直接证据的缺陷发现。**

### Q5 是否与三分类 / 同根因刹车 / Human 风险接受 / 双评审冲突？

赞同 reasonix R3（与 `pre-existing-release-critical` 的优先级须声明）。另指出**两处它判为"兼容"而我认为有文字冲突**：

1. **同根因刹车 vs §5 阶梯。** §8 要求穷举扫描"该缺陷家族在受审范围内的**全部站点（含已修与未修）**"；而拟议 §5 写"不能以'可能还有同类'为由无限扫描"。reasonix 认为"扫描是任务不是新场景"故兼容——但读者不是规则学者：被派去做穷举扫描的实现者，手上正拿着一句字面禁止它的新规则。**加一句优先级即可**：同根因刹车触发时的穷举扫描是被授权范围，本节的"不无限扫描"不适用于它。
2. **与 `reality-checker.md` 的默认姿态直接对撞。** 该文件写"**Default to finding issues unless proof shows otherwise**" + "Fail-closed when required evidence is missing"；方案写"不满足者不得发出正式 REWORK"。二者**可以**共存（一个管交付证据、一个管新场景），但只有在 `AGENTS.md` 明写这条区分时才行。见 Q6。

### Q6 三文件范围是否足够？

**足够。这是我与 reasonix 的第三处、也是最主要的分歧：我不同意 R4（给两个 reviewer skill 各加一行提醒）。**

- 理由一：`AGENTS.md` 是 §4 启动清单的第 1 项，**评审者必读**，指针纯属冗余；而 §2 Harness Design Principle 明确要求"single detailed active authority… must not copy"。加提醒行只是把 P2 的预算问题摊到更多文件。
- 理由二（更重要）：reviewer skill 里的问题**不是缺提醒，是有一句反向的话**。在"Default to finding issues"旁边加一行"须满足证据门"，得到的是两条并列且方向相反的指令——**这比只有其中任何一条都糟**，模型会按上下文临时挑一条。
- 正确解法（成本更低）：在 `AGENTS.md` 里加**一句**消歧，让 reviewer skill 完全不必动：
  > 本门只约束模型自行提出的新场景。**交付自身的证据缺失、验收检查失败、需求不符仍然 fail-closed、仍然非接受。**

  这一句同时消除了对撞、保住了三文件边界、并堵死 Q7 里最危险的误读。
- 唯一可能需要扩到第 4 个文件的情形：试运行中观察到 reviewer 确实被 skill 文本带偏。那时应当**修改 `reality-checker.md` 那一句的作用域**（它自己的权威），而不是在旁边加提醒。这符合方案 §7 自设的"说明独立职责"标准：该文件持有自己的默认 verdict 姿态，而新门修改了这个姿态。**先不动，留作试运行的触发式改动。**

### Q7 哪些文字会被误读？

赞同 reasonix 列的 5 条。按危险度补充/重排，最危险的是第 1 条：

1. **"不得发出正式 `REWORK`"**（§4）→ 读成"拿不准就 ACCEPT"。这会**反转本仓库现有的 fail-closed 默认**（`reality-checker.md`、`code-reviewer.md` Overrides "Fail-closed: if required evidence is missing, the result is non-accepting"、`AGENTS.md` §3.7）。**这是全稿最危险的一句**，修法见 Q6 的消歧句。
2. **"普通功能与资金安全问题使用同样无限展开的分析强度"**（§1.5）→ 读成"普通功能不必严谨"。应改为"**分析的展开程度**按影响分层"，而不是"**严谨程度**分层"。
3. **"最多记录为非阻塞观察"** → 变成新的倾倒场：每轮 20 条假设改个抽屉，Human 照读，60% 原地不动。必须配套：**非阻塞观察必须带重开触发条件，写进 `问题记录`，且不得出现在给 Human 的简报里**（这也是 P1 的解法之一）。
4. §5 第 6 步"验收通过后停止" → 读成"验收后看见真缺陷也不报"。补"仍须上报，只是不擅自扩大本次范围"（同 reasonix）。
5. §9 "未经要求新增的文件：目标为 0" → 与 Task Handoff Evidence Contract 自相矛盾（同 reasonix R5），须限定为实现层。
6. 术语层面：全稿"证据"一词同时指"缺陷存在的证据"与"场景可达的证据"，建议前者用"证据"、后者用"可达性凭据"，否则六项要求会被套用到普通缺陷上（即 Q4 的范围不一致）。

**有，且更小的那个更可能真的生效。**方案的形状是"加三段规则"；我的建议是"**降权一段既有文本 + 加十几行规则**"，净字节为负：

## 我的阻塞项（P1-P5）

- **P1（治理面错位，最严重）。** 方案只治正式 `REWORK` 与实现范围，但 Human 不读代码（§10），其时间几乎全部花在读模型产出的散文上：终端简报、planning 文档、评审文档。而 §7 Compact Output Rules 的 300 字硬上限**只对 `LOW_RISK` 生效**，`HIGH_RISK`/`REWORK` 显式豁免——本仓库涉及订单/持仓/划转/账务，**默认 HIGH_RISK**，即该闸门从不生效。结论：即使准入门 100% 生效，方案自设的"耗时减半"指标也达不成。
  **修法（仍在三文件内，§7 是 `AGENTS.md` 自己的章节）**：该豁免仅覆盖**证据**，不覆盖**未验证的假设场景**——假设场景一律进 `问题记录`（带重开触发条件），**不进给 Human 的简报**。现有文字已经写着"put detailed findings… in the review evidence referenced by `问题记录`/`修复要求`"，只需把"假设场景"明确纳入同一去向。
- **P2（预算未计）。** 见"总体判断"2。要求：三文件净字节 ≤ 0，写进验收标准并用 `wc -c` 核验。
- **P3（四类缺陷无法表达）。** 见 Q1，须为四类各写一条可接受的凭据形式。
- **P4（无仲裁者）。** "证据门不满足"是可争辩判断。无仲裁者时，实现者会写反驳、评审者会再主张、最后 Human 裁决——**Human 耗时上升**，与目标相反。
  **修法（零新机制）**：复用 §7 已有的 `contested`。现文字："`contested` 项必须携带：被质疑检查的原文名称、质疑理由、替代证据…Bookkeeper 必须显式裁定——驳回（走一轮修复并递增 `rework_count`）或采信（按勘误规则更正，不消耗返工预算，**因为缺陷在 packet 不在交付**）"。把同一句的适用对象扩到"由评审发现派生的验收检查"即可：缺陷在**发现**不在交付，同理不计返工。**不新增字段、不新增枚举、不新增角色，完全符合方案 §3 非目标。**
  **护栏**：命中资金安全清单的争议不得由 Bookkeeper 采信关闭，一律上交 Human。
- **P5（门是无状态的）。** 每个评审是全新只读会话，会重新推导同一批假设场景。若无"已排除场景"账本，60% 会在 2-3 个 stage 后回流。
  **修法（复用既有文件与既有写法）**：驳回一个值得记住的场景时，在 `PROJECT_STATE.md` 追加一行"事实 + 排除依据 + 重开前提"。该写法仓库已在用且已被证明有效——例如 `[BY-DESIGN] Standing operating premise: the Start gate is kept ON… **do not file it as one again**`，以及 `DEC-2026-08-07-007`（bStock 无借币市场 → 全部 `reverse + bStock` 路径不可达）。这是整个方案里**唯一会随时间变便宜**的机制，不加它，门的成本恒定。

## 试运行的可测口径（对 §9 的替代建议）

**"连续 5 个任务、必要资金安全检查遗漏目标为 0"在统计上无效**：若真实漏检基率是每 10 个 stage 约 1 次，则 5 个任务全 0 在"门有效"与"门有害"两个假设下同样是最可能结果——它无法区分二者，只能给出虚假安心。改测**高频、便宜、客观**的量：

1. 每条 `REWORK` 发现是否携带机器可核验凭据（0/1，Bookkeeper 在 `问题记录` 记一行）；
2. 每条发现最终是否被证实（修复后行为确实改变 / 被 `contested` 采信 / 被驳回）；

4. 三文件 `wc -c` 净变化（目标 ≤ 0，直接对应 P2）。

5 个任务约产生 10-20 条发现，(1)(2) 有足够样本；(3)(4) 是确定性核验。
