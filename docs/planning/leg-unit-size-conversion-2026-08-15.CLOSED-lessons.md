## 1. 为什么停

不是设计不成立。**五轮评审到最后，三方里两家明确确认「设计本身逐点核对全部成立」**，
三个阻塞项全部是**清单完整性**与**文档自相矛盾**，没有一条是「方案错了」。

停的理由是**投入产出比**：

| | 数据 |
|---|---|
| 收益 | 可对冲宇宙 358 → 364（+1.7%）；11 个月边际贡献 **1.72%**；其中 **74% 集中于 `1000XEC` 一个币**，`1000SHIB` 在 500 个结算周期内**从未达阈** |
| 投入 | 五轮设计 + 三轮三方评审已耗尽；实现估 500–800 行，触及真金白银的下单数量路径 |
| 收敛 | **每一轮都还在发现新遗漏，且发现数在增加**（见 §2） |

Human 决定：现状（fail-closed 挡着）是安全且成本为零的终态，**不继续投入**。

## 2. 核心经验：这个仓库「一个概念散在多处」的密度极高

**五轮实测记录（这是本文最有价值的部分）：**

| 轮次 | 漏了什么 | 谁发现的 |
|---|---|---|
| r1 | 「两腿价差」全部三处 | 双评审 |
| r2 | 第三处（前端） | 仅 grok |
| r3 | 两个 reverse 分支（`domain.py:1591`、`snapshot.py:699`） | 作者自查 |
| r4 | **历史页与任务卡整两个界面** | **仅 grok**（作者与另两家全漏） |
| r5 | 7 个展示格 + **1 个计算路径**（`residual`） | grok 与 claude-glm 各半 |

### 2.1 发现数不收敛，且发现者每轮不同

这是最该记住的一条。**不存在「这轮终于查全了」的时刻**——每轮都有人找到新的，
而且没有任何一个评审（包括作者）能连续两轮都是找到最多的那个。

→ **推论：单一评审者的「已查全」结论对这类问题零可信度，必须多方独立横扫。**

### 2.2 语义搜必漏；枚举基底必须是封闭可 grep 的集合

r1–r4 全部按「**两腿价差**」这个语义横扫，四轮都没找到历史页。
原因很简单：**历史页不算价差**，它显示的是逐腿的数量、价格与成交额，
搜 `spread` / `basis` / `slippage` 一个都命中不了。

r5 改成「逐格枚举」，仍然漏了 7 格——因为「逐格」靠人眼扫界面，也不是封闭集合。

**claude-glm 在最后一轮给出了正确答案：**

> 按**渲染函数族**登记（`renderHedgeAttemptLeg` / `renderHedgeLogEntryLeg` /
> `hedgeLogLegCell` / `formatHedge*` 的调用点成族列出），**勿逐格点补**。

→ **将来任何一轮这类改造，枚举基底必须是「所有渲染函数 + 所有后端逐腿量装配点」
这种封闭可 grep 的集合，不能是语义关键词，也不能是人眼扫出来的格子清单。**

## 3. 三条具体的技术经验（与 1000x 无关，普遍适用）

### 3.1 「改了反而错」的格子：名义价值不变量在展示层

```
历史页合约成交额（index.html:5386）
    = open_qty (个 1000BONK) × open_avg_price (每个 1000BONK)
    = 正确的 USDT 金额          ← 两个量纲错误方向相反，乘积天然正确
```

同构的还有历史页现货成交额（`:5391`）与任务卡逐腿明细的累计成交额。

**所有其它格子的失败模式是「不改就错」；只有这几格是「改了才错」。**
一份写着「全路径统一施加换算」的方案，会诱导实现者把这几格也改掉，
**结果是把本来对的变成错的（真值的 1/1000）**。

→ **将来做任何量纲统一时，先找出「两个错误方向相反、乘积自洽」的格子并标记禁止改动。**

### 3.2 「计算路径」与「展示路径」的默认相反

r1–r4 一直写「在开仓、平仓、平滑、**展示**的每一条路径上统一施加」。
逐格数完 25 格后发现：**22 格不该换算。**

```
计算路径（比较、判定、下单）  →  必须换算
展示路径（界面上的每一格）    →  默认原样 + 单位标注
```

判据：**该格是否会被拿去与交易所页面对账**。会对账的保持原样（否则毁掉人工核对这条
最后防线），只用于两腿互比的才换算，两者都要的则「展示原值 + 换算副本仅供公式内部用」。

→ **默认取反的代价很具体：它让实现者倾向多改，而多改正好撞上 3.1 那几格。**

### 3.3 量纲错误的单测会假绿

两个具体机制（这轮找到的）：

1. **真假执行器各持一份换算** → 两边同错则全绿。
   已在前置轮消除（收敛为 `domain.resolve_send_qty`，merge `3dc74f5`）。
2. **假执行器模拟成交给两腿喂同一个数量、同一个价**（`backend/tests/fakes.py:207-214`）
   → 走 dry-run 的持仓 / 均价 / 滑点测试全部两边同错而假绿。**未消除，仍在。**

→ **将来做量纲改造，第一步不是改实现，是先让测试能够失败**
（`fakes.py` 运行时不可达，改它零生产风险，见 `service.py:3665`）。

## 4. 流程经验

### 4.1 撤回一个改法时，必须扫下游引用

r5 撤回了「后端源头换算 `perp_avg`」，但**只改了 §3.5 主体，三处下游引用没跟着扫**：
§0 一句话结论、§3.5 尾段、**§8.2 用例 9c**（最危险——会把刚撤回的方案重新验收回去）。

**这与 r1–r4 漏的东西是同一个形状，只不过发生在文档里。**
→ 改一个决定时，`grep` 该决定的全部引用，不要只改主体段落。

### 4.2 评审模型可靠性实测（两轮记录）

| 模型 | r4 | r5 | 评价 |
|---|---|---|---|
| **grok** | REWORK 2 阻塞，**独家发现历史页** | REWORK 2 阻塞，**独家发现 `residual` 计算路径** | **最能挖。历轮阻塞项几乎全部由它找到** |
| **claude-glm** | ACCEPT 6 观察（其 O2 实为阻塞，判轻了） | REWORK 3 阻塞，**给出「按渲染函数族枚举」的正确方法** | 稳、细，偶尔定级偏轻 |
| **agy** (`gemini-3.7-flash`) | ACCEPT 0 发现，**问题 3 答案经核实为错** | ACCEPT 0 发现，**捏造核实内容** | **不可用，见下** |

**agy 在 r5 的具体问题**：它声称「清单 §8 确认的**借币日志（BONK 口径无量纲问题）、
资金流水（交易所原始账本）**、死代码等排除项成立」。而 `column-inventory.md` §8 只有
四行（持仓表不渲染 `spot_qty`/`perp_qty`、无导出/CSV、预检快照前端不渲染、
`list_fills_for_task` 无生产调用），**「借币日志」「资金流水」全文 grep 计数为 0**。

即：**它描述了一份没读过的文档，并给出「核实成立」的结论。**

→ **一个会捏造核实过程的评审比没有评审更糟——它提供虚假信心。**
将来派发深度设计评审时，`agy` 窗口的结论不得作为独立证据；
若该窗口仍跑 Flash 级模型，建议直接不派。

### 4.3 「作为裁判核实对方引用」是必须的，不是可选的

本轮三方共提出约 30 项引用，作者逐条核实的结果：
grok 与 claude-glm **引用全部属实**；agy 有捏造。
若不核实而直接采信，r5 会带着一个虚假的 ACCEPT 进入实现。
