- 日期：2026-08-08
- 评审对象：`docs/planning/ponytail-lite-harness-overthinking-2026-08-08.review-request.md`
- 评审性质：Human 直接要求的独立只读计划评审（无 stage / dispatch）。未修改任何

- 评审人：Kimi（Moonshot AI）

## 总体判断

**方向正确，可以进入 Human 决策。** 三条核心理由：

1. **准入门是"证据与可达性门"，不是"概率门"。** 方案正确地拒绝了概率阈值（模型
   估不准真实概率），改用当前相关性、可达性、实际影响、证据、处理成本做准入。这
   与本仓库既有 fail-closed 哲学同构：不看"多大概率发生"，看"路径是否真实存在"。
2. **低概率高损失保护通过了本仓库最重要的历史测试。** 1000x 乘数币两腿量纲错配
   从未真实发生（实盘库零此类仓位），但静态路径完整可证——两腿共用同一个
   `q_common`，全链路在 `compute_preflight` 可查（`backend/hedge_open_tasks/
   domain.py:1004` 一带）。在准入门第 4 条下它**仍可阻塞**。门没有误杀这个案例。
   反过来，bStock 币「reverse 不可达」曾被模型误报为 Live Risk（PROJECT_STATE
   领域事实条），正是准入门要拦的那类无可达路径报告。门的历史双向验证都成立。
3. **三文件范围与实际病灶一一对应**（详见 Q6），没有扩大，也没有遗漏。

需要修订的不是方向，而是合同文字层的若干边界。全部修订由拟议流程 step 3 的
Planner 收编即可，不需要推翻重来。修订清单见文末 R1–R8。

## 对 §11 八个问题的回答

### Q1：准入门会不会压掉必须处理的低概率高损失问题？

主体不会，但有三个必须收紧的口子，否则会被"严格读法"压掉真实风险：

**(a) 并发/交错类资金风险。** 第 4 条"静态代码路径或控制流能够证明其可达"按字面
读是单线程控制流。但资金风险的常见形态是：两个任务各自走 preflight 都"安全"，
并发执行时共用同一统一账户余额导致透支。它的可达性证明是一段**交错调度论证**，
不是"入口→分支→触发输入"的单一路径。严格读法下，评审者会被反咬"你的场景需要
两个任务同时运行，属多重前提叠加，驳回"。**必须写明：对资金路径，交错调度论证
就是控制流可达性证明。**

**(b) 误导 Human 资金决策的展示/记账错误。** §2 例外清单（资金、订单、持仓、借
还款、划转、账务含义……）若被窄读为"代码直接动钱"，那么"余额读不到却显示可用"
这类展示谎言会被当成"普通场景"弹回。本仓库刚用一整个阶段治过这个病（F4 交易所
无仓假声明、Q4 可转出额"读不到显示未知不回退"），因为 Human 看着错误展示做资金
操作，效果等同直接动钱。**例外清单应显式包含"向 Human 错误呈现资金状态的展示与
记账含义"。**

**(c) 交易所契约允许但从未出现过的外部值。** 例：UM API 返回一个文档里有、实盘
从未见过的订单状态枚举。本仓库的 `order_state_unknown_final` 处理正是为这类场景
加的。建议划一条可判定的线：**交易所文档契约允许的值 → 可达；需要交易所自身出
bug 才到的值 → 不可达。** 这条线把"多重偶然叠加"（交易所出 bug × 恰好断网 × 恰
好人工操作）干净地挡在门外，同时放行未知状态处理。

另有一个非文本的行为风险：门存在之后，模型可能连**找**都不找了。应写明准入门只
限制"阻塞交付与扩大范围"，不限制探索、记录和非阻塞观察——观察不设数量上限，永不
构成阻塞。§4 的"最多记录为非阻塞观察"已近此意，但要防止读成"不许提"。

### Q2："静态可达路径即可作为资金风险证据"的边界是否足够明确？

不够，差三句话，都在 Q1 已展开：

1. 交错调度论证算可达性证明（资金路径）；
2. 交易所契约允许值算可达，交易所自身出 bug 才算不可达；
3. **可达性争议的仲裁方向**：资金路径上，评审者与实现者对可达性各执一词时，默认
   按可达处理（fail-closed），除非反驳方能给出一条可执行命令证伪；非资金路径上
   的争议默认降级为非阻塞观察并写明重开触发信号。这样争议不会卡在"谁去说服谁"
   上，而是落到现成的观察机制里。

### Q3："便宜验证 / fail-closed"会不会成为无限加检查的借口？

**会，这是全方案最容易被反向利用的一条。** 每个假设场景都可以伪装成"就加一个便
宜的 assert"重新溜进来。"成本很低"没有定义，不同模型对"便宜"的判断差一个数量
级。收紧三件套：

1. **客观定义"便宜"**：现有函数内的一个断言或守卫 + 现有测试内的一个断言。不得
   新增函数、文件、配置项、状态字段、日志种类。凡需要新增其中任何一样的，都不
   走第 5 条，回第 1–4 条正常过门。
2. **允许的是"对具名不变量的断言"，不是"对假设场景的检查"。** 断言"两腿数量相
   等""余额不为负""读不到显示未知"——不变量断言对*没想过的*场景也有效；场景检
   查只对*想象到的*场景有效，后者才是过度思考的温床。本仓库 Q4 的 self-check 断
   言组就是不变量断言的正确形态。
3. **只打日志不拦截 ≠ fail-closed。** 一个只写日志的检查制造的是无人盯的新信
   号，比没有更糟（告警疲劳）。要么指明日志读者与处置动作，要么不算数。

### Q4：六项证据要求是否过重、重复、仍可被绕过？

不过重，结构也没重复；真正的风险是**形式上填满、内容不可核验**。评审者可以每项
写一句话，句句无法证伪。收紧方法：给六项加"可核验句"要求——

- 入口、可达性：必须是 `file:line` 引用，"用户可能……""未来可能……"句式自动不
  合格；
- 实际影响：必须点名具体错值——哪个字段、哪笔账、哪笔单错成什么样，"资金可能受
  损"不算；
- 验证 oracle：三选一——可执行命令、可执行测试、含行号的静态调用链；
- 最小修复边界（第 6 项最容易被糊弄）：必须回答"本轮不修、留作后续项，会多出什
  么实际损害？"答不出实质损害的，就是后续项。

另需保持现状的一点是：六项要求只适用于"用一个**新场景**阻塞交付"。已复现缺陷、
验收标准内问题不适用此表——评审稿 §6 已这样限定，写进合同时别丢这个限定，否则
每次评审都变成填表运动。

### Q5：与范围三分类、同根因刹车、Human 风险接受、双评审是否冲突？

逐一核对，无实质冲突，但有两处需要一句话级别的隔离，外加一个**本评审发现的真
正结构问题**：

- **范围三分类**：兼容。但要写明准入门只约束 `in-range` 的 REWORK 判定；
  `pre-existing-*` 的分类与升级路径不变——特别是 `pre-existing-release-critical`
  上报 Human 的通道**不受准入门影响**。否则评审者会拿门把"历史遗留但涉及资金"
  的发现也挡回去。
- **同根因刹车**：兼容，评审稿 §6/§8 已保留。反向也要防一句：穷举扫描轮按根因
  模式枚举站点，**不要求每个站点独立满足准入门**——否则门会杀死刹车。现有表述
  只防了"用最小修改原则逃避扫描"这一个方向。
- **Human 风险接受**：兼容。本仓库现成实例：open-spot-usdt-transfer 阶段的
  「Human 决断（勿议）」清单（不查余额、不幂等、不自动回流、不做前端防重）。
  评审者重提这些就该被门挡住，§8 案例表已覆盖此情形。
- **双评审**：兼容，§6 已显式保留。
- **结构问题（本评审唯一的新发现）**：`AGENTS.md` §1 已经存在同族原则——"Do not
  add abstractions... for hypothetical scenarios"，并且自带一份例外清单（"Known
  live exposure, money risk, open gates, missing close capability, observed model
  mismatch, proven review gaps, cheap validation, and fail-closed safety still
  require action"）。评审稿 §2/§4 要写的是**第二份**例外清单，措辞与粒度都不同
  （新增信任边界、凭据、风险限额等）。在 `AGENTS.md` 里放两份"假设场景禁令 +
  例外清单"，直接违反 Harness §2 的单一权威原则。**实施时必须合并：场景准入门是
  §1 既有原则的展开，例外清单只保留一份、只有一个家。** 顺带说明：§1 的 "cheap
  validation" 早已预见了第 5 条，这正说明新规则该长在 §1 旁边而不是另起炉灶。

### Q6：三文件范围是否足够？

足够，且与实际病灶一一对应，反对扩大：

- `AGENTS.md`：准入门是工作流合同，证据门属 §8 Review Rules——位置正确，但须按
  Q5 与 §1 合并，不是另起段落。
- `agents/developer-discipline.md`：阶梯属实现方法——位置正确。注意该文件 §2
  "Simplicity First" 已有 "No error handling for impossible scenarios" 等同族条
  款，**阶梯应并入 §2 而不是新增平行章节**，否则同一文件内出现两套简洁性权威。
- `agents/skills/senior-developer.md`：**这是三处改动里单位价值最高的一处。**
  vendored 文本 actively 指挥过度工程——"**Default requirement**: Include
  comprehensive security measures and monitoring in **all** systems"、熔断器、死信
  队列、分布式追踪全部列为必须遵守的 Critical Rules。加一行 Harness Override 把
  它们降级为"证据触发的能力清单"，正是该文件既有 override 区的既定用法。
- Reviewer 三件套（code-reviewer / reality-checker / security-reviewer）：我逐一
  核实过，三者的 Harness Override 已有"结果与评审收口字段以 `AGENTS.md` 为准、
  不得在此复制"的指针模式，且 `AGENTS.md` 是启动第一步必读。证据门写进 §8 后评
  审者自然读到，**一行提醒都不必加**——评审稿"仅当证明必要"的条件，我的判断是
  不必要。
- `software-architect.md`：其 Critical Rules 第 1 条已是 "No architecture
  astronautics"，评审稿不动它的判断正确。
- `minimal-change-engineer.md`（修复 skill）：discipline 文件头本就覆盖
  "implementation and fix work"，"修根因必须证明共享根因"的边界写进 discipline
  即同时约束实现与修复，无需另改。

### Q7：哪些文字会被误读为"忽略边界场景"或"为少写代码牺牲正确性"？

- **标题与 §1 的"60%"叙事。** 模型记住的将是"治理过度思考"，忘掉的是例外清单。
  合同正文的顺序应该**先写保留项、后写限制项**：先声明资金安全例外永不被门挡，
  再定义门。
- **§4"不得修改当前交付；不得发出正式 REWORK"。** 会被读成"不得记录、不得提
  及"。补一句：探索、记录与非阻塞观察不受限制。
- **§5 阶梯第 6 步"验收通过后停止"。** 会被读成跳过测试直接交差。补一句：验收
  包含测试与证据，停止的是范围扩张，不是验证。
- **§9"未经要求新增的抽象、文件和依赖：目标为 0"。** 指标为 0 会激励把逻辑塞进
  现有函数制造更差的代码（指标博弈）。补一句：指标是观察用不是配额，review-1 照
  常按质量审。
- **§5 阶梯的"已安装依赖"一阶。** 评审稿附加边界已有"已安装依赖并不自动优于少
  量本地代码"，这句防误读必须保留进最终合同。
- **§2 例外清单若漏掉展示/记账含义**（Q1(b)），"涉及资金"会被窄读成"代码直接
  动钱"。

### Q8：是否存在更小、同样可验收的整改方案？

我考虑过三个更小的候选，都不成立：

- **只改 `AGENTS.md`（砍掉阶梯与 skill 覆盖）**：前提是问题几乎全在评审侧。但
  §1 问题清单明确包含实现侧的范围扩大，且 `senior-developer.md` 的一行 override
  是单位价值最高的改动，砍了可惜。
- **只写 §8 证据门 + skill 一行，阶梯不进 discipline**：discipline §2 现有文字
  太抽象（"No error handling for impossible scenarios"），过去一个月它没能阻止
  Human 观察到的行为；阶梯是它的可操作版本，砍掉等于赌同样的文字这次会生效。
- **每次 dispatch 口头注明**：问题跨模型、跨阶段反复出现，口头要求不持久，合同
  才是对的载体。

结论：**三文件方案已是充分小的持久方案。** 真正的最小化发生在合同文字层——合并
`AGENTS.md` §1、合并 discipline §2、reviewer skills 零改动。

## 建议新增的验收案例

在 §8 案例表基础上新增六条（前三条守"门不误杀"，后三条守"门不被绕"）：

| 场景 | 预期处理 |
|---|---|
| 两任务并发共用统一账户余额，单看各自路径都"安全"，存在交错调度透支 | 交错论证即资金可达性证明，可阻塞 |
| 余额/持仓读不到却显示"可用"，诱导 Human 误操作 | 命中资金例外（误导资金决策的展示含义），可阻塞 |
| 交易所文档契约允许但实盘从未出现的枚举值（参照 `order_state_unknown_final`） | 资金路径按可达处理，不以"未发生"驳回 |
| 为理论场景新增配置项 + 恢复链，自称"很便宜" | 违反第 5 条"不扩大契约/制造新恢复状态"，非阻塞 |
| 新增只打日志、无人盯处置的检查，自称 fail-closed | 不构成 fail-closed，除非指明日志读者与处置动作 |
| Reviewer 重提 Human 已"勿议"事项（如不幂等、不自动回流）且前提未变 | 不重复阻塞；引用既有接受记录关闭 |

另对 §9 试运行提一条：连续 5 个任务中应至少含 1 个资金路径任务，否则"必要资金
安全检查遗漏：目标为 0"这条指标无从验证。

## 评审结论

```text
计划评审结论: ACCEPT
阻塞问题: none
安全反例: none（1000x 乘数币等低概率高损失场景在准入门下仍可阻塞；三条须收紧的可达性边界属合同文字修订，见 R2/R3）
最小修改建议: 保持三文件范围不扩大；两处必须合并（AGENTS.md §1 同族原则与例外清单、developer-discipline.md §2 Simplicity First），reviewer skills 零改动
建议验收案例: 新增六条（并发交错资金场景、展示误导资金场景、交易所契约允许值、便宜检查走私、只打日志不算 fail-closed、Human 勿议事项重提），另建议试运行 5 任务至少含 1 个资金路径任务
```

`ACCEPT` 只表示计划可进入 Human 决策，不授权实施、合并、部署或实盘操作。R1–R8
是合同起草时的收编清单，不是阻塞项。
