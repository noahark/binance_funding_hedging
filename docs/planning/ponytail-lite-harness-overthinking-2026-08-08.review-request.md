# 模型过度思考与刁钻 REWORK 场景治理（Ponytail-lite，需求与计划评审稿）

- **日期**：2026-08-08
- **状态**：待独立、跨 provider、只读计划评审
- **风险分类**：HIGH_RISK（Harness 工作流契约拟议变更）
- **当前权限**：仅记录需求和候选方案；未授权修改 Harness、代码、服务或任何实盘状态
- **来源**：Human 直接提出的近一个月开发体验；`60%` 与 `<1%` 是 Human 经验估计，不是已采样统计

---

## 1. Human 的实际问题

最近一个月开发中，模型经常对极低概率、前置条件刁钻、当前没有证据的场景投入过多分析，并把部分场景升级为实现要求或正式 `REWORK`。Human 估计约 60% 的协作时间消耗在发生概率低于 1% 的场景上。

这不是要求模型停止考虑边界条件。需要治理的是：

1. 仅凭“理论上可能”扩大当前任务范围；
2. 没有可达路径、实际影响或验证方法仍阻塞交付；
3. 为多重偶然条件叠加的场景增加抽象、配置、恢复链、兼容层或大范围防御；
4. 反复重提 Human 已明确接受的限制或已排除的领域路径；
5. 普通功能与资金安全问题使用同样无限展开的分析强度。

## 2. 目标

建立一个可执行的“场景准入门”，让模型可以发现罕见问题，但只有具备当前相关性、可达性、实际影响和足够证据的问题，才允许：

- 扩大当前实现范围；
- 增加新的防御机制；
- 阻塞交付；
- 在正式评审中给出 `REWORK`。

同时必须保留低概率高损失保护：资金、订单、持仓、借还款、划转、账务含义、凭据、实盘闸门、破坏性数据动作、风险限额、缺失关仓能力、信任边界和已知数据损失风险，不能因为发生概率低而被机械忽略。

## 3. 非目标

本轮不做以下事项：

- 不安装或 vendoring 整套 Ponytail 插件；
- 不以 Ponytail 替换 `software-architect.md`；
- 不引入 `lite/full/ultra` 模式；
- 不采用“一行代码优先”或硬性代码行数指标；
- 不设置统一的概率阈值，模型也不负责猜测真实发生概率；
- 不降低安全验证、数据一致性、错误状态、可审计性和可访问性要求；
- 不新增 `status.json` 字段、正式 verdict 枚举、角色或永久计数器；
- 不在本评审稿中决定具体合同文字或授权实施。

## 4. 候选原则：场景准入门

模型提出的新场景，满足以下任一条件时，才可以进入当前实现或成为阻塞性评审问题：

1. 当前需求或验收标准明确要求；
2. 已发生、可复现，或有真实日志、样本、交易所行为、现有测试失败等证据；
3. 能给出当前代码中的完整可达路径，包括前置状态、入口、关键分支、触发输入和实际影响；
4. 涉及资金、安全、数据损失或缺失关仓能力，且静态代码路径或控制流能够证明其可达；
5. 验证或 fail-closed 防护成本很低，并且不会扩大契约或制造新的恢复状态。

若均不满足：

- 不得修改当前交付；
- 不得发出正式 `REWORK`；
- 不得要求增加抽象、配置、依赖、兼容层或恢复链；
- 如确有保留价值，最多记录为非阻塞观察，并写明未来重新打开它所需的真实触发信号。

“可能发生”本身不是证据。“概率很低”本身也不是忽略理由；决定因素是当前可达性、影响、证据、处理成本及是否命中资金安全例外。

## 5. 候选原则：项目版 Ponytail 决策阶梯

实现模型在写代码前按以下顺序判断：

1. 读清当前需求、非目标、验收标准和实际执行链；
2. 判断改动是否属于当前任务，或满足场景准入门；
3. 查找代码库中已有的权威模块、数据源、执行路径或共享根因；
4. 判断标准库、平台原生能力或已安装依赖能否保持现有语义并完成任务；
5. 选择最小、清晰、可审计的实现，不做代码高尔夫；
6. 验收通过后停止，不顺手重构或补建未来能力。

附加边界：

- Human 已批准的需求不能由 Implementer 自行缩水；
- 修根因必须证明共享根因和实际受影响站点，不能以“可能还有同类”为由无限扫描；
- 资金数量、单位换算、精度、取整方向、部分成功、未知状态、关仓能力和审计证据不参加代码量删减；
- 已安装依赖并不自动优于少量本地代码，选择依据仍是当前正确性、维护成本和现有项目惯例。

## 6. 正式评审的证据要求

Reviewer 若要用一个新场景阻塞交付，应明确提供：

1. **入口**：从哪个真实调用、状态或外部输入进入；
2. **可达性**：当前代码和配置为何能到达该分支；
3. **前置条件**：需要哪些状态同时成立；
4. **实际影响**：对 Human、资金、数据或当前验收产生什么效果；
5. **验证 oracle**：可执行测试、命令、原始证据路径，或足够明确的静态控制流证明；
6. **最小修复边界**：为什么必须在本次交付修，而不是非阻塞后续项。

单纯的“如果未来……”“理论上……”“建议更健壮……”不得构成 `REWORK`。涉及资金等高风险路径时，不要求等待真实事故；明确的静态可达路径可以作为证据。

本规则不得削弱现有的：

- 发现范围三分类；
- `base_sha..delivery_sha` 固定评审范围；
- 同根因连续两轮后的穷举扫描；
- Human 已知风险接受记录；
- review-1 / review-2 分工及 HIGH_RISK 双评审。

## 7. 拟修改的单一权威与文件边界

若计划评审通过，候选实现只触碰以下三个文件：

| 文件 | 唯一职责 | 候选改动 |
|---|---|---|
| `AGENTS.md` | 通用准入和正式评审合同 | 写入场景准入原则；在 Review Rules 中要求阻塞问题满足证据门 |
| `agents/developer-discipline.md` | 实现阶段详细最小化方法 | 写入项目版 Ponytail 阶梯和验收后停止规则 |
| `agents/skills/senior-developer.md` | 实现 skill 的项目优先级覆盖 | 明确 vendored 的规模化、熔断、追踪、迁移等是证据触发的能力清单，不是默认交付物；指向 developer discipline，不复制规则 |

本轮原则上不修改：

- `agents/skills/software-architect.md`：现有内容已经要求拒绝无依据抽象；
- `agents/skills/task-planner.md`：Planner 的最小范围要求已有上位权威；
- Reviewer skills：只允许增加指向 `AGENTS.md` 的一行提醒，且仅当计划评审证明缺少提醒会导致执行失败；不得复制证据字段清单。

若评审认为必须扩大上述文件范围，应说明缺失职责、读者、维护者和为何现有权威无法承载。

## 8. 验收案例

候选合同至少应正确处理以下案例：

| 场景 | 预期处理 |
|---|---|
| 已有测试或日志复现普通缺陷 | 当前任务处理，不能以“低概率”拒绝 |
| 静态可达的订单、持仓、划转、账务或无法关仓风险 | 即使尚未发生，也可阻塞并要求 fail-closed 或 Human 决策 |
| 需要多个未出现前提同时成立、无调用路径证明的普通场景 | 不扩大实现，不得 `REWORK` |
| 与当前领域事实冲突、代码路径不可达的场景 | 驳回；不得为了它增加防御代码 |
| 一个便宜断言即可验证的关键不变量 | 应验证，不以 YAGNI 删除 |
| Reviewer 只写“未来规模扩大时可能不够” | 非阻塞；未来出现真实负载证据时再开 |
| 连续两轮正式 `REWORK` 命中同一根因 | 仍执行现有穷举根因扫描，不得用最小修改原则逃避 |
| Human 已明确接受且前提未变化的限制 | 不重复阻塞；只有接受前提变化时重开 |
| 修复一个共享根因比在多个调用方打补丁更小 | 修共享根因，并核对实际调用点 |
| “一行实现”会隐藏单位、取整、部分成功或未知状态 | 采用较长但清晰可审计的实现 |

## 9. 试运行与效果判断

通过全部 Harness 评审后，建议用连续 5 个正常任务做试运行；该数量只用于本次验证，不写成永久合同限额。

观察指标：

- 无可达性或证据的阻塞问题：目标为 0；
- 未经要求新增的抽象、文件和依赖：目标为 0；
- 必要资金安全检查遗漏：目标为 0；
- Human 感受到的假设场景讨论耗时：从当前估计约 60% 至少降低一半；
- 因过度简化造成的正式返工或真实事故：目标为 0。

若分析时间没有明显下降，优先收紧 Reviewer 的阻塞证据要求。若开始遗漏真实风险，调整资金安全例外和可达性证明方法，不采用概率阈值，也不直接撤销整个准入门。

## 10. 拟议流程

1. Human 确认本需求与非目标；
2. 独立、跨 provider 的高级模型进行只读计划评审；
3. Planner 根据评审修订方案；计划评审勘误不计 `rework_count`；
4. Human 决定是否建立正式 stage 和 implementation dispatch；
5. Implementer 仅修改批准文件并自测；
6. Bookkeeper 封存固定 `base_sha..delivery_sha`；
7. 因 Harness 合同变更属于 HIGH_RISK，执行 review-1 与 review-2；
8. 两轮均 `ACCEPT` 后，由 Human 决定是否启用试运行；不自动合并、部署或改变实盘状态。
